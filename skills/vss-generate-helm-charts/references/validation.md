## Safety boundary

Allowed checks are local/read-only or authoring-only:

- `compose_helm_context.py`
- `validate_chart_structure.py`
- YAML parsing
- `docker compose config` (configuration rendering only)
- `helm dependency update/build` (chart metadata/packages only)
- `helm lint`
- `helm template`
- `kubeconform` or equivalent against rendered files
- repository tests that do not start workloads

Never run Compose lifecycle commands, Helm release commands, or Kubernetes mutation commands. Do not use server-side dry runs because they contact a cluster. Render output under a temporary directory and remove it after review.

## Gate 1: source and directive coverage

1. Re-run `compose_helm_context.py` with the exact original scope.
2. Confirm the selected and related source file lists cover includes, env layers, configs, scripts, and assets.
3. Require zero malformed directives.
4. Match every valid directive and ordinary deployment-related comment to a ledger row.
5. Match every changed/deleted service and source file to a ledger row.
6. Review the raw Git diff for deleted source behavior that cannot be scanned from the worktree.

Use `docker compose config` only when its env inputs can be supplied without secrets and the static tool is available. Do not treat its output as comment coverage.

## Gate 2: repository structure

Run the bundled validator for each changed primary root and consumer:

```bash
python3 skills/vss-generate-helm-charts/scripts/validate_chart_structure.py \
  --repo-root . --chart deploy/helm/services/agent --recursive
```

The validator checks chart metadata, local dependency paths/names/versions, lock consistency, values roots, template file references, unresolved Compose interpolation, and basic file layout. Resolve all errors. Review every warning; suppress nothing merely because it predates the current change if the affected chart was edited in that area.

Also run:

```bash
git diff --check
git status --short
```

Confirm all changed files are expected and no generated secret, temporary render, packaged chart, or unrelated artifact was added.

## Gate 3: dependencies and versions

For each local dependency edge:

1. Child `Chart.yaml` name equals dependency `name` (unless only the values key changes through `alias`).
2. Child version equals parent dependency version.
3. Parent `condition` exists in the correct values root and the intended profile enables/disables it.
4. `Chart.lock` dependency tuple and digest are regenerated by Helm after metadata changes.
5. Version propagation continues through every transitive parent.

When Helm is available, update/build only affected chart dependencies. Review the resulting diff; do not commit ignored `.tgz` packages or cache artifacts.

Do not fabricate or manually calculate a lock digest. An unavailable dependency or network/cache miss is a validation blocker, not permission to leave a stale lock while claiming success.

## Gate 4: lint and render matrix

Run `helm lint` and `helm template` for each affected leaf chart, service umbrella, and developer/industry profile. Cover all relevant values combinations:

- Default `values.yaml`
- Every install-oriented `values-*.yaml`
- Every `override-values*.yaml`
- Mode variants such as realtime/verification
- Hardware variants such as H100/L40S/RTX PRO/DGX/Thor when affected
- NodePort/build-endpoint/Ingress variants when affected
- Enabled and disabled branches for newly optional resources
- Existing-secret and create-secret branches without supplying a real secret
- Persistence create/existing/disabled branches when changed
- Release-name-prefix branches when the chart supports them

Example static pattern; adapt filenames to the chart:

```bash
helm lint deploy/helm/developer-profiles/dev-profile-base \
  -f deploy/helm/developer-profiles/dev-profile-base/values-base.yaml

helm template test-release deploy/helm/developer-profiles/dev-profile-base \
  -f deploy/helm/developer-profiles/dev-profile-base/values-base.yaml \
  --namespace test-namespace > /tmp/vss-helm-render.yaml
```

Use placeholder values only for template-required non-secret inputs. Never insert a real credential. If a chart intentionally uses `lookup`, cluster capabilities, or CRDs unavailable offline, isolate and document that limitation while still rendering all other branches.

## Gate 5: manifest schema and semantic checks

When `kubeconform` is available, validate each rendered bundle with the target Kubernetes version. Use `-ignore-missing-schemas` only for genuine CRDs and review every ignored kind.

Inspect rendered manifests for these invariants:

- No remaining Helm delimiters or unintended `${VAR}` Compose interpolation
- No plaintext credentials or credential-like defaults
- Every workload selector matches its pod labels
- Every Service selector selects the intended pod and every target port exists
- Peer endpoints use Service DNS/ports, not Compose host ports or `localhost`
- Required configs, Secrets, service accounts, PVCs, and referenced names render in the same branch
- Optional disabled resources leave no dangling references
- Probes use valid local ports/paths and have a slow-start budget where needed
- Init waits are bounded and point at enabled dependencies
- Jobs have correct restart/backoff/hook/delete semantics
- PVC mounts, read-only flags, subPaths, modes, access modes, and existing-claim branches are coherent
- GPU resources and scheduling values render only for intended modes
- No unjustified host paths, host networking, privileged mode, broad capabilities, or cluster-wide RBAC
- Ingress hosts/paths/backend services agree with profile public URL contracts
- Resource names and labels meet DNS/label length and character limits
- Config/Secret changes trigger rollout when required

Use focused text assertions for high-risk facts from the ledger, but verify the containing resource rather than matching an isolated string.

## Gate 6: parity diff review

Review the final diff in dependency order:

1. Leaf values and bundled files
2. Leaf templates
3. Service umbrella values/dependencies/lock
4. Profile values and replacing lists
5. Profile-only templates/configs/Ingress/secrets
6. Transitive dependency versions/locks

Search for both the old and new identifiers. Old image tags, env names, ports, service names, config filenames, or values keys can remain intentionally only with a ledger explanation.

Reconcile every ledger row against rendered output and mark it complete. A chart is “statically validated” only when the complete render matrix passes. “Runnable” still requires later validation in an authorized target environment; this skill never performs that deployment.

## Unavailable tools

If Docker Compose is unavailable, inspect raw includes/env layers and report that effective Compose rendering was skipped.

If Python 3 or PyYAML is unavailable, do not install it implicitly. Perform manual source/dependency checks, report both bundled helper gates as skipped, and do not claim complete static validation.

If Helm is unavailable, run the bundled structural validator and repository checks, but report dependency-lock regeneration, lint, and template rendering as blockers. Do not call the chart fully validated.

If schema tooling is unavailable, inspect manifests manually and report schema validation as skipped. Never install tools or contact a cluster without separate authorization.
