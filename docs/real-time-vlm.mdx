## Overview

The Real-Time VLM Server is a FastAPI-based REST API service that provides
real-time video understanding capabilities using Vision Language Models
(VLM). It enables users to generate captions, process live video streams,
and manage live streams through a comprehensive set of REST endpoints.

For the 3.3.0 release, use the multi-architecture RTVI-VLM 26.08.1 image:
`nvcr.io/nvstaging/vss-core/vss-rt-vlm:3.3.0-26.08.1`.

<Note>
RTVI-VLM does not support cosmos-reason1 in VSS 3.3.
</Note>

The server translates between HTTP requests/responses and the underlying
Real-Time VLM Microservice components, providing a clean API
interface for live stream processing operations.

## Key Features

* **VLM Caption Generation**: Generate captions and alerts using Vision Language
  Models for live streams
* **Live Stream Support**: Process RTSP live streams for real-time caption generation and alert detection — see [Supported Inputs](/real-time-vlm#supported-inputs)
* **Streaming Responses**: Server-Sent Events (SSE) for streaming output or Kafka messages
* **Asset Management**: Comprehensive stream lifecycle management
* **Shared RTSP Decode**: Multiple caption requests can subscribe to one RTSP
  decode pipeline when their decode settings match
* **Sampling Rate Management**: Manage the image frames sampling for VLM inference of the live stream
* **Health Monitoring**: Health check endpoints for service monitoring
* **Metrics**: Prometheus metrics endpoint for observability

## Architecture

The following diagram illustrates the DeepStream Accelerated Pipeline architecture
for the Real-Time VLM Microservice:

![DeepStream Accelerated Pipeline Architecture](/assets/images/real-time-vlm/real-time-vlm.png)

The pipeline processes camera streams through the following stages:

* **RTSP + Decode**: Receives and decodes camera streams. Matching caption
  requests for the same RTSP stream share one live decode pipeline.
* **Video Segment Creation**: Creates video segments for processing
* **Infer**: Performs inference using VLM models (with vLLM inference engine)
* **MsgBroker (NvSchema)**: Publishes messages to Kafka

The system can be configured and controlled via:

* **REST API**: HTTP-based API for configuration and control

## Supported Inputs

RTVI-VLM accepts live streams and file-based media through the following input
types.

**Streaming protocols**

* **RTSP** — live camera streams managed via `POST /v1/streams/add` and
  processed via `POST /v1/generate_captions` with a `liveStreamUrl`.

**URL schemes for file-based processing**

`POST /v1/generate_captions` and `POST /v1/files` accept a `url` field
supporting the following schemes:

* `http://` and `https://` — publicly accessible or auth-protected URLs
* `s3://` — Amazon S3 object paths
* `file://` — local filesystem paths (requires `FILE_URL_ALLOWED_DIRS`)

See [URL-Based Processing](/real-time-vlm#url-based-processing) for API details and
security constraints.

**Media types**

* Video — pass `media_type: "video"` (default)
* Images — pass `media_type: "image"`

**Video Codecs**:

* H.264 (AVC)
* H.265 (HEVC)
* AV1 (hardware decode by default; set `FORCE_SW_AV1_DECODER=true` on
  platforms without hardware AV1 support)
* VP8
* VP9

**Image Formats**:

* JPEG
* PNG

**Audio**

Native audio decoding is available when using Omni models with
`VLM_MODEL_SUPPORTS_AUDIO=true`. Set `INSTALL_PROPRIETARY_CODECS=true`
when inputs may contain proprietary audio codecs. See
[Omni Native Audio Support](/real-time-vlm#omni-native-audio-support) for configuration
details.

## API Reference

For complete API documentation including all endpoints, request/response
schemas, and interactive examples, see the [Real-Time VLM API Reference ](/real-time-vlm-api).

The API is organized into the following categories:

* **Captions**: Generate VLM captions and alerts for videos and live streams
* **Files**: Upload and manage video/image files
* **Live Stream**: Add, list, and manage RTSP live streams
* **Stream**: CV-compatible stream add, remove, and list APIs
* **Config**: Update generated-message and error-message output routing
* **Models**: List available VLM models
* **Health Check**: Service health and readiness probes
* **Metrics**: Prometheus metrics endpoint
* **Metadata**: Service metadata and version information
* **NIM Compatible**: OpenAI-compatible endpoints for interoperability

| Endpoint | Method | Description |
| --- | --- | --- |
| `/v1/metrics` | `GET` | Get Prometheus-format RTVI metrics |
| `/v1/ready` | `GET` | Get Real-Time VLM Microservice readiness status |

| `/v1/startup` | `GET` | Get Real-Time VLM Microservice startup status |
| `/v1/assets/stats` | `GET` | Get asset storage statistics |
| `/v1/metadata` | `GET` | Get Real-Time VLM Microservice metadata |

### Quick Start

Clone the blueprint repository and check out the release tag:

```bash
git clone https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization.git
cd video-search-and-summarization
git checkout tags/v3.3.0
```

Then follow the Docker Compose or Helm Chart section below. The RTVI-VLM
container used by this release is tagged `3.3.0-26.08.1`.

### Docker Compose Deployment

1. Change into the service Docker directory:

   ```bash
   cd services/rtvi/rt-vlm/docker
   ```

2. Create a `.env` file with your configuration:

   ```bash
   cat > .env << EOF
   BACKEND_PORT=8000
   RTVI_IMAGE=nvcr.io/nvstaging/vss-core/vss-rt-vlm:3.3.0-26.08.1
   VLM_MODEL_TO_USE=cosmos-reason3
   MODEL_PATH=ngc:nim/nvidia/cosmos3-nano-reasoner:bf16-final
   MESSAGE_BUS=kafka
   MESSAGE_BUS_TOPIC=mdx-vlm-captions
   KAFKA_PORT=9092
   KAFKA_BOOTSTRAP_SERVERS=kafka:9092
   KAFKA_INCIDENT_TOPIC=mdx-vlm-incidents
   ERROR_BUS=kafka
   ERROR_MESSAGE_TOPIC=mdx-vlm-errors
   NGC_API_KEY=nvapi-XXXXXX
   VLM_BATCH_SIZE=128
   NVIDIA_VISIBLE_DEVICES=0
   EOF
   ```

3. Start the service:

   ```bash
   docker compose up
   ```

<Note>
The standalone Compose stack starts RTVI-VLM, Kafka, and Redis. To use a
different Kafka server, set `KAFKA_BOOTSTRAP_SERVERS`. To expose Kafka on
a custom host port, set `KAFKA_PORT`. To use a different Redis server,
set `REDIS_HOST` and `REDIS_PORT`. To expose Redis on a custom host
port, set `REDIS_HOST_PORT`.

If the launch fails due to Out of Memory error, see [Troubleshooting](/real-time-vlm#troubleshooting) (adjust `VLLM_GPU_MEMORY_UTILIZATION`,
reduce `VLM_MAX_MODEL_LEN`, or set `NVIDIA_VISIBLE_DEVICES=<gpuid>`).
</Note>

The APIs are available at `http://<HOST_IP>:<BACKEND_PORT>/docs`.

   ```bash
   kubectl create secret docker-registry ngc-image-pull-secret \

   kubectl create secret generic ngc-api \
     --from-literal=NGC_API_KEY="$NGC_API_KEY" \
     -n vss-rtvi

   kubectl create secret generic hf-token-secret \
     --from-literal=HF_TOKEN="$HF_TOKEN" \
     -n vss-rtvi
   ```

3. Install the chart with the standalone override:

   ```bash
   helm upgrade --install vss-rtvi-vlm . \
     -n vss-rtvi \
     -f overrides_rtvi_vlm.yaml
   ```

   When using the `hf-token-secret` secret, set
   `hfTokenSecret.name=hf-token-secret` and `hfTokenSecret.key=HF_TOKEN` in

4. Expose the API for local testing:

   ```bash
   kubectl port-forward -n vss-rtvi svc/vss-rtvi-vlm 8000:8000
   ```

The API is available at `http://localhost:8000/docs`.

## Usage Examples

### Required Packages

The Python examples require the following packages. Install with:

```bash
pip install requests sseclient-py
```

* **requests** – HTTP client for all examples
* **sseclient-py** – Server-Sent Events client (required only for streaming examples)

The RTVI CLI client uses additional packages (`tabulate`, `tqdm`, `pyyaml`) for

<Note>
**Discovering the loaded model ID:** The examples below use `nim_nvidia_cosmos3-nano-reasoner_bf16-final` as the
`model` field. When running a locally deployed model, the service loads it under its
full NGC artifact ID (e.g., `nim_nvidia_cosmos3-nano-reasoner_bf16-final`).
Use `GET /v1/models` to retrieve the exact ID before making inference requests:

```python
import requests
response = requests.get("http://localhost:8000/v1/models")

```

Replace `nim_nvidia_cosmos3-nano-reasoner_bf16-final` in the examples below with the returned `id`.
</Note>

### Dense Captioning Example

The following example demonstrates dense captioning for a stored video file.
A video is uploaded, split into temporal chunks based on `chunk_duration`
and `chunk_overlap_duration`, and each chunk is processed by the VLM.

**Workflow:** For a video of duration *D* seconds with `chunk_duration=60`
and `chunk_overlap_duration=10`, the video is chunked into overlapping
segments (e.g., a 120-second video yields approximately 2 chunks). Each chunk
is decoded, frames are sampled, and the VLM generates a caption. With
`stream=False` (default), all chunks are processed and returned together
in a single JSON response.

```python
import requests
import json

BASE_URL = "http://localhost:8000/v1"

# Step 1: Upload a video file
with open("video.mp4", "rb") as f:
    response = requests.post(
        f"{BASE_URL}/files",
        files={"file": f},
        data={
            "purpose": "vision",
            "media_type": "video",
            "creation_time": "2024-06-09T18:32:11.123Z"
        }
    )
response.raise_for_status()
file_info = response.json()
file_id = file_info["id"]
print(f"Uploaded file: {file_id}")

# Step 2: Generate captions (chunks returned in full response)
caption_request = {
    "id": file_id,
    "prompt": "Describe what is happening in this video",
    "model": "nim_nvidia_cosmos3-nano-reasoner_bf16-final",
    "chunk_duration": 60,
    "chunk_overlap_duration": 10,
    "enable_audio": False
}
response = requests.post(
    f"{BASE_URL}/generate_captions",
    json=caption_request
)
response.raise_for_status()
captions = response.json()
print(f"Generated {len(captions['chunk_responses'])} caption chunks")

# Step 3: Process results
for chunk in captions["chunk_responses"]:
    print(f"[{chunk['start_time']} - {chunk['end_time']}]: {chunk['content']}")

# Step 4: Clean up
requests.delete(f"{BASE_URL}/files/{file_id}")
print("File deleted")
```

### Dense Captioning (Streaming) Example

The following example demonstrates dense captioning for a live RTSP stream
with streaming output. As the stream is decoded in real time, it is split
into chunks (e.g., 60-second segments with 10-second overlap). Each chunk
is processed by the VLM as it becomes available.

**Workflow:** With `stream=True`, chunks are returned incrementally via
Server-Sent Events (SSE). Each SSE event contains `chunk_responses` for
chunks that have completed VLM inference. The client receives captions
as they are generated instead of waiting for the entire stream to finish.
The stream terminates with a `[DONE]` message.

**Concurrent RTSP caption requests:** each `/v1/generate_captions` request
for an RTSP stream ID gets its own request ID, prompt, SSE response stream,
and VLM generation path. Requests for the same RTSP stream share one live
decode pipeline when these decode settings match: `chunk_duration`, frame
sampling mode/value, `vlm_input_width`, `vlm_input_height`, and
`enable_audio`. A request with different decode settings for an already
active stream is rejected with HTTP 400; stop the active request or stream
before changing those settings. To stop one caption subscriber while keeping
others active, call `DELETE /v1/generate_captions/{stream_id}?request_id=<request_id>`.
Calling `DELETE /v1/generate_captions/{stream_id}` without `request_id`
stops the single active caption request for that stream, and returns HTTP 409
when multiple caption requests are active.

```python
import requests
import json
import sseclient

BASE_URL = "http://localhost:8000/v1"

# Step 1: Add live stream
stream_request = {
    "streams": [{
        "liveStreamUrl": "rtsp://example.com/stream",
        "description": "Main warehouse camera"
    }]
}
response = requests.post(
    f"{BASE_URL}/streams/add",
    json=stream_request
)
response.raise_for_status()
stream_info = response.json()
if stream_info.get("errors"):
    raise RuntimeError(f"Failed to add stream: {stream_info['errors']}")
stream_id = stream_info["results"][0]["id"]
print(f"Added stream: {stream_id}")

# Step 2: Start caption generation with streaming
caption_request = {
    "id": stream_id,
    "prompt": "Describe what is happening in this live stream",
    "model": "nim_nvidia_cosmos3-nano-reasoner_bf16-final",
    "stream": True,
    "chunk_duration": 60,
    "chunk_overlap_duration": 10
}
response = requests.post(
    f"{BASE_URL}/generate_captions",
    json=caption_request,
    stream=True
)
response.raise_for_status()

# Step 3: Process streaming responses (chunks as they complete)
client = sseclient.SSEClient(response)
for event in client.events():
    data = event.data.strip() if event.data else ""
    if data == "[DONE]":
        break
    if not data:
        continue
    result = json.loads(data)
    if "chunk_responses" in result:
        for chunk in result["chunk_responses"]:
            print(f"[{chunk['start_time']}]: {chunk['content']}")

# Step 4: Stop processing and remove stream
requests.delete(f"{BASE_URL}/generate_captions/{stream_id}")
requests.delete(f"{BASE_URL}/streams/delete/{stream_id}")
print("Stream removed")
```

### Deleting Streams and Resource-In-Use Responses

Stop active caption generation before deleting a live stream. If a stream or
file asset is still being used by an active request or in-flight cleanup, delete
APIs can report `ResourceInUse` with status code `409`.

`DELETE /v1/streams/delete/{stream_id}` and `POST /v1/stream/remove` return
a top-level HTTP 409 when the matched stream asset is still in use.
`POST /v1/stream/remove` uses `camera_id` to find the stream; VIOS-style
remove requests for an unknown camera are idempotent and return `asset_id=""`
instead of 404.

`DELETE /v1/streams/delete-batch` returns HTTP 200 with a mixed
`deleted`/`errors` response. If one stream cannot be removed because it is
in use, that stream appears in `errors` with `status_code` set to `409`
and `error_code` set to `ResourceInUse`; other streams in the batch can
still be deleted.

```json
{
  "deleted": ["11111111-1111-1111-1111-111111111111"],
  "errors": [
    {
      "stream_id": "22222222-2222-2222-2222-222222222222",
      "error": "Resource 22222222-2222-2222-2222-222222222222 is currently being used",
      "error_code": "ResourceInUse",
      "status_code": 409
    }
  ]
}
```

For teardown workflows, first stop the caption request with
`DELETE /v1/generate_captions/{stream_id}` and then delete the stream. For
batch cleanup, use `blocking=true` to wait for live-stream pipeline drain up
to `drain_timeout_seconds` or `RTVI_STREAM_DELETE_BLOCKING_TIMEOUT_SEC`. If
a `ResourceInUse` error remains, retry after the active request or cleanup
drain completes.

```json
{
  "stream_ids": [
    "11111111-1111-1111-1111-111111111111",
    "22222222-2222-2222-2222-222222222222"
  ],
  "blocking": true,
  "drain_timeout_seconds": 300
}
```

### CV- and VIOS-Compatible Stream API

In addition to the `/v1/streams/*` endpoints, RTVI-VLM exposes a
CV-/VIOS-compatible stream API for cross-service interoperability with other
VSS services: `POST /v1/stream/add`, `POST /v1/stream/remove`, and
`GET /v1/stream/get-stream-info`.

These endpoints accept two payload shapes:

* **Direct CV-compatible payload**: `{key, value, headers}`, where
  `value` contains `camera_id`, `camera_url`, `change`, and optional
  metadata. Use this when an application calls RTVI-VLM directly.
* **VIOS event payload**: `{alert_type, created_at, source, event}`, where
  `event` carries the camera fields. Use this when forwarding VIOS
  camera-status events.

For existing VIOS camera flows, the hidden aliases ``POST
/api/v1/camera/add` and `PUT /api/v1/camera/streaming`` use the same add
handler. `POST` and `DELETE /api/v1/camera/remove` use the same remove
handler. Prefer the documented `/v1/stream/*` endpoints for new
integrations; the compatibility API is evolving and its request and response
schema can change between releases.

For both payload shapes, `metadata.prompt` starts VLM inference automatically
after the stream is added. Omit `metadata` or omit `metadata.prompt` to add
the stream without starting inference. `camera_url` accepts RTSP URLs,
`file://` URLs, HTTP(S) URLs, and, for VIOS file sensors, absolute file
paths. File URLs and paths must be allowed by `FILE_URL_ALLOWED_DIRS`.

Direct CV-compatible add/remove example:

```python
import requests

BASE_URL = "http://localhost:8000/v1"

payload = {
    "key": "sensor",
    "value": {
        "camera_id": "camera-entrance-east-01",
        "camera_url": "rtsp://example.com/stream",
        "change": "camera_add",
        "camera_name": "Entrance Camera",
        "metadata": {
            "prompt": "Describe what is happening in this live stream",
            "chunk_duration": 10
        }
    },
    "headers": {
        "source": "vios"
    }
}
response = requests.post(f"{BASE_URL}/stream/add", json=payload)
response.raise_for_status()
result = response.json()
# result: {"camera_id": "...", "asset_id": "...", "status": "processing", "inference": true}

requests.post(
    f"{BASE_URL}/stream/remove",
    json={
        "key": "sensor",
        "value": {
            "camera_id": "camera-entrance-east-01",
            "change": "camera_remove"
        }
    }
)
```

VIOS event add/remove example:

```python

BASE_URL = "http://localhost:8000/v1"

vios_add_payload = {

# result: {"camera_id": "...", "asset_id": "...", "status": "processing", "inference": true}

vios_remove_payload = {

    "created_at": "2026-07-29T00:00:00Z",
```

For VIOS `POST /v1/stream/add` requests, `change` can be
`camera_streaming` or `camera_add`. A VIOS `camera_add` event with
`camera_url` set to an empty string is accepted as registration-only and
returns `status="added"` with `inference=false`. For
`POST /v1/stream/remove`, `change` can be `camera_remove` or `remove`;
VIOS remove requests for an unknown camera return `asset_id=""` instead of
a 404 response.

| Feature | `POST /v1/streams/add` | `POST /v1/stream/add` |
| --- | --- | --- |
| Schema style | VLM-native | CV-/VIOS-compatible |
| When to use | RTVI-VLM standalone integrations | Multi-service deployments and VIOS camera-status events |
| Auto-starts VLM inference | No - call `/v1/generate_captions` separately | Yes, when `metadata.prompt` is set |
| Response schema | `{results: [{id}], errors: []}` | `{camera_id, asset_id, status, inference}` |
| Stream removal endpoint | `DELETE /v1/streams/delete/{stream_id}` | `POST /v1/stream/remove` |

### VLM Alert Example

The following example demonstrates alert/anomaly detection using the VLM.
Use a prompt that expects a structured Yes/No response for anomaly detection.
When anomalies are detected, incidents can be published to the Kafka incident
topic (see [Kafka Integration](/real-time-vlm#kafka-integration)). The Incident
message payload is defined in [Incident Messages](/real-time-vlm#incident-messages).

```python
import requests

# Upload video or use existing stream ID

        "wasting time. Respond in the following structured format:\n"
        "Anomaly Detected: Yes/No\n"
```

### URL-Based Processing

`POST /v1/generate_captions` and `POST /v1/files` accept a `url`
field for direct server-side ingestion without a prior upload step.
Supported schemes: `http://`, `https://`, `s3://`, and `file://`.

**New request fields on /v1/generate_captions:**

* `url` — media URL (any supported scheme).
* `media_type` — `"video"` (default) or `"image"`.
* `creation_time` — ISO 8601 timestamp used as the frame-time offset
  baseline (useful for live-correlated archive playback).
* `url_headers` — per-request authorization headers (dict). HTTPS only;
  cross-domain redirects strip these headers.

**New response field:** each chunk in `chunk_responses` includes a
zero-based `chunk_id` for ordering.

**Security:**

* `file://` URLs are rejected unless `FILE_URL_ALLOWED_DIRS` is set
  (comma-separated absolute directories). Paths are resolved via
  `realpath` to prevent traversal escapes.
* HTTP/HTTPS URLs are validated against SSRF rules. Per-domain SSL skip
  is opt-in via `ASSET_DOWNLOAD_SSL_SKIP_VERIFY_DOMAINS`. Redirect hops
  are disabled by default; raise the cap via `ASSET_DOWNLOAD_MAX_REDIRECTS`
  (max 10). Server-level auth tokens can be set per domain via
  `ASSET_DOWNLOAD_AUTH_TOKENS` (format:
  `domain1=Bearer token1;domain2=Basic xyz`).

```python
import requests

BASE_URL = "http://localhost:8000/v1"

caption_request = {
    "url": "https://example.com/video.mp4",
    "media_type": "video",
    "creation_time": "2024-06-09T18:32:11.123Z",
    "prompt": "Describe what is happening in this video",
    "model": "nim_nvidia_cosmos3-nano-reasoner_bf16-final",
    "chunk_duration": 60,
    "chunk_overlap_duration": 10
}
response = requests.post(
    f"{BASE_URL}/generate_captions",
    json=caption_request
)
response.raise_for_status()
for chunk in response.json()["chunk_responses"]:
    print(f"[chunk {chunk['chunk_id']}] {chunk['content']}")
```

## Implementation Details

### Server Class

The RTVI-VLM Server implements the FastAPI application and manages
all API endpoints.

### Timestamp Handling

The server handles timestamps differently based on media type, for live stream uses NTP timestamps (ISO 8601 format).

### Streaming Implementation

For streaming responses, the server uses Server-Sent Events (SSE):

* Events are sent as JSON objects
* Each event contains chunk responses as they become available
* Final event contains usage statistics (if requested)
* Stream terminates with `[DONE]` message
* Multiple clients can caption the same RTSP stream concurrently. Each
  `/v1/generate_captions` call gets its own request ID, prompt, SSE response
  stream, and VLM generation path. Matching requests share one live RTSP
  decoder; mismatched decode settings are rejected until the active request or
  stream is stopped.

## Kafka Integration

The Real-Time VLM Microservice can publish messages to Kafka topics for downstream
processing. This enables integration with other microservices, analytics
pipelines, and real-time alerting systems.

### Kafka Topics

The server publishes to the following Kafka topics:

* **VisionLLM Messages** (default: `mdx-vlm-captions`): Contains
  VisionLLM protobuf messages with VLM caption results.
* **Incidents** (default: `mdx-vlm-incidents`): Contains Incident
  protobuf messages when anomalies or incidents are detected.
* **Errors** (default: `mdx-vlm-errors`): Contains error event messages
  when stream processing failures occur.

**Configuration:**

Generated-message output is controlled by the following environment variables:

* **MESSAGE_BUS**: Generated-message output bus. Set to `kafka`,
  `redis`, or empty to disable generated-message output in the service
  runtime. The standard Docker Compose deployment defaults this value to
  `kafka`.
* **MESSAGE_BUS_TOPIC**: Topic or Redis stream for VisionLLM messages. Default:
  `mdx-vlm-captions`. This is the primary per-chunk output stream and
  replaces the legacy `KAFKA_TOPIC` setting.
* **KAFKA_BOOTSTRAP_SERVERS**: Comma-separated list of Kafka broker
  addresses (e.g., `localhost:9092` or `kafka:9092` for Docker). Required
  when `MESSAGE_BUS=kafka` or `ERROR_BUS=kafka`.
* **KAFKA_INCIDENT_TOPIC**: Kafka-only topic for Incident messages. Default:
  `mdx-vlm-incidents`. Incident messages are published only when an anomaly
  is detected. This topic is independent of `MESSAGE_BUS_TOPIC`.
* **ERROR_BUS**: Error-message output bus. Set to `kafka` (default),
  `redis`, or empty to disable error-message output.
* **ERROR_MESSAGE_TOPIC**: Topic/channel for error messages. Default:
  `mdx-vlm-errors`.

### Generated-Message Bus Startup Selection

In 26.08.1, `MESSAGE_BUS` is the startup source of truth for generated-message
output. `KAFKA_ENABLED` is removed from the active RTVI-VLM startup path, and
`KAFKA_TOPIC` is replaced by `MESSAGE_BUS_TOPIC`.

To enable Kafka generated-message output:

```bash
MESSAGE_BUS=kafka
MESSAGE_BUS_TOPIC=mdx-vlm-captions
KAFKA_BOOTSTRAP_SERVERS=<host>:<port>
```

To enable Redis generated-message output:

```bash
MESSAGE_BUS=redis
MESSAGE_BUS_TOPIC=<redis-stream-name>
REDIS_HOST=<host>
REDIS_PORT=6379
```

To disable generated-message bus output in the service runtime, leave
`MESSAGE_BUS` unset or set it to empty. In the packaged Docker Compose
deployment, `MESSAGE_BUS` defaults to `kafka`; leaving it unset or empty in
`.env` still expands to `kafka`. Use a Compose override or update the
service environment to set `MESSAGE_BUS: ""` when generated-message output
must be disabled. The performance Compose deployment sets `MESSAGE_BUS` empty
by default.

### Runtime Config API

Use `POST /v1/config` to update generated-message routing at runtime from a
VSS-style config event. Kafka and Redis connection details are still configured
at startup; the runtime API switches the active generated-message bus/topic and,
optionally, the active error-message bus/topic.

```json
{
  "alert_type": "config",
  "created_at": "2026-07-29T00:00:00Z",
  "txn_id": "txn-001",
  "source": "vios",
  "event": {
    "change": "config",
    "metadata": {
      "messagingbus": "kafka",
      "topic-prefix": "mdx-vlm-captions",
      "errorbus": "kafka",
      "error-topic-prefix": "mdx-vlm-errors",
      "create-topic": false
    }
  }
}
```

The config payload fields map to runtime routing as follows:

* `alert_type` must be `config` and `event.change` must be `config`.
* `event.metadata.messagingbus` is required and must be `kafka` or
  `redis`. It selects the active generated-message output bus.
* `event.metadata.topic-prefix` is required. RTVI-VLM uses it as the actual
  Kafka topic or Redis Stream name for VisionLLM messages.
* `event.metadata.errorbus` is optional. When present, it selects the active
  error-message output bus.
* `event.metadata.error-topic-prefix` is optional. When present with
  `errorbus`, it sets the Kafka topic or Redis channel for error messages.
* `event.metadata.create-topic` and `event.metadata.topic-partition` are
  best-effort Kafka topic creation controls. They are ignored for Redis.

The endpoint changes only message routing. Kafka bootstrap servers, Redis
host/port/database, credentials, the active model, prompts, and
`KAFKA_INCIDENT_TOPIC` remain startup configuration. The runtime Config API is
not the startup disable path; use `MESSAGE_BUS` at startup to enable or
disable generated-message bus output. If routing is changed while caption
requests are active, messages already queued can still publish to the previous
route, while subsequent chunk messages use the updated route.

### How Alerts and Incidents Are Sent to Kafka

When `generate_captions` processes video chunks, the server publishes
messages to Kafka as each chunk completes VLM inference:

1. **VisionLLM messages** are sent to `MESSAGE_BUS_TOPIC` when
   `MESSAGE_BUS=kafka`. Each message
   contains the VLM caption, frame metadata, sensor info, and an
   `incidentDetected` flag in the `info` map (`"true"` or `"false"`).
   When reasoning is enabled and parsed from the VLM output, the reasoning is
   also added to the `info` map as both `reasoning` and
   `reasoningDescription`.

2. **Incident messages** are sent to `KAFKA_INCIDENT_TOPIC` only when an
   anomaly is detected. The server detects incidents by checking the VLM
   response for trigger phrases such as `"yes"` or `"true"`
   (case-insensitive). Use prompts that expect structured Yes/No answers (see
   [Enabling Incidents](/real-time-vlm#enabling-incidents)). For the full
   Incident message payload (protobuf schema and example), see
   [Incident Messages](/real-time-vlm#incident-messages).
   When reasoning is available, it is also added to `Incident.info` as both
   `reasoning` and `reasoningDescription`.

3. **Publishing flow** (per chunk):

   * After VLM inference completes, the server builds a VisionLLM protobuf and
     optionally an Incident protobuf if the response triggers an alert.
   * Each message is sent asynchronously with a key
     `{request_id}:{chunk_idx}` for partitioning and ordering.
   * A `message_type` header (`"vision_llm"` or `"incident"`) identifies
     the payload type for consumers.
   * VisionLLM and Incident messages are published independently; an incident
     is sent only when the VLM output indicates an anomaly.

4. **Requirement**: Set `MESSAGE_BUS=kafka` and configure
   `KAFKA_BOOTSTRAP_SERVERS` for Kafka publishing to occur.

### Message Formats

#### Incident Messages

Incident messages are serialized as Protocol Buffer (protobuf) messages
using the `Incident` message type from the protobuf schema.

**Message Header:**

* **message_type**: `"incident"`

**Message Structure:**

```protobuf
message Incident {
  string sensorId = 1;
  google.protobuf.Timestamp timestamp = 2;
  google.protobuf.Timestamp end = 3;
  repeated string objectIds = 4;
  repeated string frameIds = 5;
  Place place = 6;
  AnalyticsModule analyticsModule = 7;
  string category = 8;
  repeated Embedding embeddings = 9;
  bool isAnomaly = 10;
  LLM llm = 12;
  map<string, string> info = 11;
}
```

**Key Fields:**

* **sensorId**: Identifier of the sensor/stream
* **timestamp**: Start timestamp of the incident
* **end**: End timestamp of the incident
* **objectIds**: Array of object IDs involved in the incident
* **category**: Category of the incident (e.g., `"safety_non_compliance"`)
* **isAnomaly**: Boolean indicating if the incident is an anomaly
* **llm**: LLM query and response information
* **info**: Additional metadata map containing fields like:
  * `request_id`: Request ID associated with the incident
  * `chunk_idx`: Chunk index where the incident was detected
  * `incident_detected`: Alert flag
  * `reasoning`: Parsed VLM reasoning, when available
  * `reasoningDescription`: Parsed VLM reasoning, when available
  * `priority`: Priority level (e.g., `"high"`)

**Example Incident JSON (for reference):**

```json
{
  "sensorId": "camera-entrance-east-01",
  "timestamp": "2025-11-19T06:22:20Z",
  "end": "2025-11-19T06:22:32Z",
  "objectIds": [],
  "frameIds": ["frame-10512", "frame-10518"],
  "place": {
    "id": "dock-entrance-east",
    "name": "Dock Entrance - East",
    "type": "warehouse-bay"
```

#### VisionLLM Messages

VisionLLM messages contain VLM caption results and are serialized as
Protocol Buffer messages using the `VisionLLM` message type.

**Message Header:**

* **message_type**: `"vision_llm"` (default, if not specified)

**Message Structure:**

See the protobuf schema documentation for complete `VisionLLM` message
structure. Key fields include:

* **version**: Message version
* **timestamp**: Start timestamp
* **end**: End timestamp
* **startFrameId**: Start frame identifier
* **endFrameId**: End frame identifier
* **sensor**: Sensor information
* **llm**: LLM queries, responses, and embeddings
* **info**: Additional metadata map. When reasoning is enabled and parsed from
  the VLM output, this map includes both `reasoning` and
  `reasoningDescription`.

### Redis Error Messages

By default, error messages are sent to Kafka through `ERROR_BUS=kafka`.
To use Redis for error messages, set the following environment variables in
your `.env` file:

```bash
ERROR_BUS=redis
REDIS_HOST=redis.example.com
REDIS_PORT=6379
REDIS_DB=0
REDIS_PASSWORD=your_password  # Optional, only if Redis requires authentication
ERROR_MESSAGE_TOPIC=mdx-vlm-errors  # Redis channel name for error messages
```

Error messages will be published to the Redis channel specified in
`ERROR_MESSAGE_TOPIC`. The message format remains JSON with the following
fields: `streamId`, `timestamp`, `type`, `source`, `event`.
`ENABLE_REDIS_ERROR_MESSAGES=true` is still accepted as a legacy alias for
`ERROR_BUS=redis` when `ERROR_BUS` is unset.

### Omni Native Audio Support

Omni models, including Nemotron Nano Omni, provide native single-model video +
audio understanding. When `VLM_MODEL_SUPPORTS_AUDIO=true` is set, audio is
decoded and consumed natively by the model alongside video frames.

**Required environment:**

```bash
VLM_MODEL_TO_USE=vllm-compatible
MODEL_PATH=<HF or NGC path to Nemotron Nano Omni>
VLM_TRUST_REMOTE_CODE=true
VLM_MODEL_SUPPORTS_AUDIO=true   # omit for video-only

```

<Note>
Set `INSTALL_PROPRIETARY_CODECS=true` when audio inputs may contain
proprietary audio codecs. Without it, the service falls back to the
default codec set and may fail to decode the audio track of such
inputs. The flag has no effect when audio is disabled.
</Note>

**Request side:** pass `enable_audio: true` on `POST /v1/generate_captions`
to use native audio. For reasoning checkpoints, set
`enable_reasoning: true`; the response includes a `reasoning_description`
field in each chunk.

**Response side:** each chunk in `chunk_responses` includes an
`audio_transcript` field (when `enable_audio` is set). Native audio
understanding is available only on Omni models; other VLM models support
video and text input only.

For LVS integration, see [Optional: Use Nemotron-3-Nano-Omni (audio-aware VLM)](/agent-workflow-lvs#optional-use-nemotron-3-nano-omni-audio-aware-vlm).

### Efficient Video Sampling (EVS and EVS++)

EVS is a vLLM-engine feature that prunes redundant video tokens before
inference to reduce per-chunk compute. RTVI-VLM supports two startup modes:

* **Fixed-rate EVS**: Set `VLM_VIDEO_PRUNING_RATE` to a value greater than
  `0` and less than `1`. For example, `0.5` prunes about half of the
  redundant video tokens. Leave it unset or set it to `0` to disable this
  mode.
* **EVS++ session mode**: Set both `VIA_EVS_SESSION=true` and
  `VLM_VIDEO_PRUNING_RATE=0.5`. `VIA_EVS_SESSION` routes requests through
  the vLLM video-session path, while `VLM_VIDEO_PRUNING_RATE` activates
  pruning in the engine at startup. The RTVI-VLM build applies the EVS++ vLLM
  overlay for this session mode. It adds content-dependent similarity pruning,
  per-stream video sessions, event-gated generation, token-budgeted clip
  packing, absolute timestamp metadata, and optional Prefill-Decode (PD)
  server routing.

EVS settings are read at service startup, so restart the RTVI-VLM service after
changing them. They are not changed by the runtime Config API.

```bash
# Fixed-rate EVS
VLM_VIDEO_PRUNING_RATE=0.5

# EVS++ session mode
VIA_EVS_SESSION=true
VLM_VIDEO_PRUNING_RATE=0.5
VLLM_EVS_SIMILARITY_THRESHOLD=0.2
```

Fixed-rate EVS is available on vLLM-compatible local models that use the
patched video-pruning paths, including Nemotron Nano VL, Qwen 2.5-VL, and
Qwen3-VL/Cosmos3-style models. EVS++ is supported only for local,
vLLM-compatible models based on the Qwen3-VL architecture. It is not
applicable to `openai-compat` remote endpoints and is not supported for
Omni models, including `NemotronH_Nano_Omni_Reasoning_V3`.

### Frame Selection Modes

RTVI-VLM supports two frame selection modes for sampling frames from video
chunks:

**FPS-based Selection:**

* Enable `--use-fps-for-chunking` flag
* Set `--num-frames-per-second-or-fixed-frames-chunk` to the desired frames
  per second (e.g., `0.05` for 0.05 FPS)
* The system will sample frames at the specified rate based on chunk duration

**Fixed Frame Selection (default):**

* Do not set `--use-fps-for-chunking` flag (disabled by default)
* Set `--num-frames-per-second-or-fixed-frames-chunk` to the desired number
  of frames per chunk (e.g., `8` for 8 frames)
* The system will sample a fixed number of equally-spaced frames from each chunk

`media_io_kwargs` can also control frame sampling on
`/v1/generate_captions` and `/v1/chat/completions`. Positive
`media_io_kwargs.video.fps` or `media_io_kwargs.video.num_frames` values
override `num_frames_per_second_or_fixed_frames_chunk` and
`use_fps_for_chunking`. Use `num_frames=-1` to select all decoded frames
in a chunk. `fps` and `num_frames` are mutually exclusive.

```json
{"media_io_kwargs": {"video": {"fps": 3.0}}}
{"media_io_kwargs": {"video": {"num_frames": 16}}}
{"media_io_kwargs": {"video": {"num_frames": -1}}}
```

## Troubleshooting

### Common Issues

**Container fails to start**

* Check `docker logs <container_name>` for error messages
* Verify GPU access: Ensure NVIDIA Container Toolkit is installed and
  `nvidia-smi` works

**Out of Memory error**

For example, larger models such as
`Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16` may need these
settings on NVIDIA RTX 4500, L40S, or Thor systems.

* Set `NVIDIA_VISIBLE_DEVICES=<gpuid>` to a free GPU
* **Reduce batch size**: Try `VLM_BATCH_SIZE=32` Default is auto-calculated
* **Tune GPU memory utilization**: Lower `VLLM_GPU_MEMORY_UTILIZATION` when
  model startup OOMs. Increase it only when KV-cache capacity is too low and
  free GPU memory remains.
* **Reduce max sequences**: Lower `VLLM_MAX_NUM_SEQS`
* **Reduce concurrent processes**: Lower `NUM_VLM_PROCS`
* **Reduce max model length on lower-memory GPUs**: Reduce `VLM_MAX_MODEL_LEN`
* **Cap generation length**: Lower `VLM_MAX_GENERATION_TOKENS` (default
  `16384`) to bound peak per-request memory.
* On Jetson Thor or DGX systems, ensure that the [cache cleaner](/prerequisites#cache-cleaner-only-on-dgx-spark-igx-thor-and-agx-thor) script is running.

If the issue persists, reduce the image preprocessor `max_pixels` value for
the affected model. Replace `<model-cache-directory>` with the directory
name for the model in the RTVI NGC model cache:

```bash
docker compose run --rm --no-deps --entrypoint sh rtvi-server

MODEL=/opt/nvidia/rtvi/.rtvi/ngc_model_cache/<model-cache-directory>

cp "$MODEL/preprocessor_config.json" "$MODEL/preprocessor_config.json.bak"

python3 -c 'import json; p="'"$MODEL"'/preprocessor_config.json"; d=json.load(open(p)); d["max_pixels"]=802816; open(p,"w").write(json.dumps(d,indent=2)+"\n")'

grep -n '"max_pixels"' "$MODEL/preprocessor_config.json"
exit
```

**Thor workaround for huge-model OOM**

When running huge models such as
`Nemotron-3-Nano-Omni-30B-A3B-Reasoning-BF16` on AGX Thor or
IGX Thor, allocate host swap before starting the RTVI-VLM service:

```bash
sudo fallocate -l 96G /swapfile-nemotron
sudo chmod 600 /swapfile-nemotron
sudo mkswap /swapfile-nemotron
sudo swapon --priority 10 /swapfile-nemotron
```

Use conservative vLLM memory settings in Docker Compose `.env` or Helm
`env` values:

```bash
VLM_MAX_MODEL_LEN=2560
VLLM_GPU_MEMORY_UTILIZATION=0.55
```

Also ensure that the [cache cleaner](/prerequisites#cache-cleaner-only-on-dgx-spark-igx-thor-and-agx-thor) script is
running on Thor.

**System memory grows over time**

For long-running workloads with many distinct videos or streams, keep the
multimodal preprocessor cache disabled.

Docker Compose `.env`:

```bash
VLLM_DISABLE_MM_PREPROCESSOR_CACHE=true
```

Helm chart `env` values:

```yaml
env:
  - name: VLLM_DISABLE_MM_PREPROCESSOR_CACHE
    value: "true"
```

Restart the service after changing these values. Re-enable the multimodal
preprocessor cache only after validating memory behavior for your workload.

**Port conflicts**

* Change `BACKEND_PORT` if port 8000 is already in use

**Kafka Connection Issues**

* Use `kafka:9092` as bootstrap server when connecting from within
  Docker network
* Verify Kafka is running: `docker ps | grep kafka`

**Health Check Failures**

* Check logs with `docker compose logs rtvi-vlm`

### Known Issues

**High concurrency with 8K vision tokens on Jetson Thor / DGX Spark**

When running more than 2 concurrent live streams with a high vision-token
budget (~8K vision tokens, i.e., 448×448 at 80 frames with Cosmos Reason3),
the device may reboot or the microservice may crash due to memory pressure on
resource-constrained edge platforms.

* **Recommendation:** Limit concurrent live streams to 2 or fewer when using
  8K vision tokens on Jetson Thor or DGX Spark.
* Alternatively, reduce the vision-token budget by lowering the input
  resolution from 448×448 to 372×372 at 30 frames (~2K vision tokens) using
  `VLM_INPUT_WIDTH=372`, `VLM_INPUT_HEIGHT=372`,
  `VLM_DEFAULT_NUM_FRAMES_PER_SECOND_OR_FIXED_FRAMES_CHUNK=30` to support
  higher concurrency.

**Stream deletion latency and ResourceInUse responses under high concurrent load**

When multiple live streams are being processed concurrently and the VLM
inference latency exceeds the chunk duration (e.g., processing takes longer
than the configured `chunk_duration`), deleting a stream via
`DELETE /v1/streams/delete/{stream_id}`,
`DELETE /v1/streams/delete-batch`, or `POST /v1/stream/remove` may take
longer than expected or report `ResourceInUse` with status code `409`.

* This is expected behavior: the server avoids tearing down resources that are
  still held by active caption generation or cleanup.
* For single-stream delete and CV-/VIOS-compatible remove, `ResourceInUse` is
  returned as a top-level HTTP 409. For batch delete, it is returned per stream
  in the response `errors` list.
* Stop active caption requests first, then retry after the drain completes. For
  batch cleanup, set `blocking=true` when the caller should wait for pipeline
  drain before the response is returned.
* The delay is proportional to the VLM inference time at the current load.
  Reducing concurrency or increasing `chunk_duration` will reduce delete
  latency.

**Duplicate live-stream / camera IDs rejected with HTTP 409**

In 3.2.0, adding a stream with a `camera_id` (CV API) or `streamId`
that is already registered returns HTTP 409 (`DuplicateCameraId` /
`DuplicateStreamId`). In 3.1.0 the existing registration was silently
overwritten. Update client code to either remove the prior stream first
or surface the 409 to the caller.
