## Overview

The Video Summarization microservice processes uploaded video files through
[RTVI-VLM](/system-components/vision-microservices/real-time-vlm) for per-chunk vision inference and a summarization LLM (CA-RAG) for
event aggregation. The tables below report mean end-to-end (E2E) latency for file summarization,
with and without EVS++, maximum concurrent request capacity on data center GPUs, and
latency at 1, 2, and 4 concurrent requests on DGX Spark and AGX Thor.
Use these numbers to size GPU count and topology for batch summarization workloads on B200, H100,
L40S, RTX Pro 6000 SE, and RTX Pro 4500 SE GPUs, and on DGX Spark and AGX Thor.

| Parameter | Value |
| --- | --- |
| VSS release | 3.3 |
| VLM | Cosmos3 Nano Reasoner, Cosmos3 Super Reasoner |
| Model precision | NVFP4 (B200, RTX Pro 6000 SE, RTX Pro 4500 SE, DGX Spark, AGX Thor), FP8 (H100, L40S) |
| Summarization LLM | Nemotron 3 Nano (B200, H100, L40S, RTX Pro 6000 SE); Nemotron-Nano-9B-v2 (1-GPU H100, RTX Pro 4500 SE as a remote endpoint, DGX Spark, AGX Thor) |
| EVS++ | Off, or on with `VIA_EVS_SESSION=true` and `VLM_VIDEO_PRUNING_RATE=0.5` |
| Chunk duration | 10 seconds |
| Frames per chunk | 20 |
| Vision input tokens | 9k |
| Output max tokens | 100 |
| GPU topologies | 2 GPUs (VLM on one GPU, LLM on the other); 1 GPU (VLM and LLM on the same GPU, or VLM only with a remote LLM); DGX Spark and AGX Thor run the VLM and LLM on the same device |
| Platforms tested | B200, H100, L40S, RTX Pro 6000 SE, RTX Pro 4500 SE, DGX Spark, AGX Thor |

<Note>
All measurements use 20 frames per 10-second chunk, 9k vision tokens, and `max_tokens=100`.
With EVS++ on, VLM input tokens per chunk drop from about 10.1k to about 2.3k (vision and prompt
tokens combined).

1-GPU settings: with the LLM on the same GPU, the VLM uses `RTVI_VLLM_GPU_MEMORY_UTILIZATION=0.35`
and the LLM is limited to 40% of GPU memory. RTX Pro 4500 SE uses
`RTVI_VLLM_GPU_MEMORY_UTILIZATION=0.45`, `RTVI_VLLM_MAX_NUM_BATCHED_TOKENS=2048`, and
`RTVI_VLM_ADMISSION_MODE=adaptive`.

AGX Thor runs in the MAXN power mode with clocks pinned (`sudo nvpmodel -m 0` and
`sudo jetson_clocks`). Lower power modes give longer latencies.
</Note>
