This section covers the prerequisites for deploying and using the VSS Blueprint.

## Hardware Requirements

The VSS Blueprint has been validated and tested on the following NVIDIA GPUs:

- NVIDIA H100
- NVIDIA GB300
- NVIDIA RTX PRO 6000 Blackwell
- NVIDIA L40S
- NVIDIA DGX SPARK
- NVIDIA IGX Thor
- NVIDIA AGX Thor
- NVIDIA RTX PRO 4500 Blackwell (limited support to alerts profile)

For GPUs that are not validated and tested, the OTHER configuration is available (experimental). See the deployment steps in each workflow guide for the GPU tab options.

If you need to know which platforms support your use-case, see the [Performance](/vss/appendix/performance) section for benchmark results across models, use cases, and GPU platforms.

<Note>
If you're looking for a pre-configured environment to try out the VSS Blueprint, please refer to the [Brev Launchable](/vss/appendix/additional-deployments/brev-launchable) section.
</Note>

## Runtime Environment Settings

In addition to the above prerequisites, the following runtime environment settings are required:

### Linux Kernel Settings

```bash
# Ensure the sysctl.d directory exists
sudo ls -l /etc/sysctl.d

# Write VSS kernel settings to 99-vss.conf (persistent across reboots)
sudo bash -c "printf '%s\n' \
  'net.ipv6.conf.all.disable_ipv6 = 1' \
  'net.ipv6.conf.default.disable_ipv6 = 1' \
  'net.ipv6.conf.lo.disable_ipv6 = 1' \
  'net.core.rmem_max = 5242880' \
  'net.core.wmem_max = 5242880' \
  'net.ipv4.tcp_rmem = 4096 87380 16777216' \
  'net.ipv4.tcp_wmem = 4096 65536 16777216' \
  > /etc/sysctl.d/99-vss.conf"

# Reload sysctl to apply the new settings
sudo sysctl --system
```

### Power Mode (only on IGX-THOR and AGX-THOR)

```bash
# Set max power mode
# NOTE: the below command requires a reboot to take effect
sudo nvpmodel -m 0
```

After reboot:

```bash
# Set max clocks
sudo jetson_clocks
```

<Note>
The above is reset to default settings if the system is rebooted.
</Note>

### Cache cleaner (only on DGX-SPARK, IGX-THOR and AGX-THOR)

Run the cache cleaner script for DGX SPARK and Jetson Thor.

Create the cache cleaner script at `/usr/local/bin/sys-cache-cleaner.sh`:

```bash
sudo tee /usr/local/bin/sys-cache-cleaner.sh << 'EOF'
#!/bin/bash
# Exit immediately if any command fails
set -e

# Disable hugepages
echo "disable vm/nr_hugepage"
echo 0 | tee /proc/sys/vm/nr_hugepages

# Notify that the cache cleaner is running
echo "Starting cache cleaner - Running"
echo "Press Ctrl + C to stop"
# Repeatedly sync and drop caches every 3 seconds
while true; do
	sync && echo 3 | tee /proc/sys/vm/drop_caches > /dev/null
	sleep 3
done
EOF

sudo chmod +x /usr/local/bin/sys-cache-cleaner.sh
```

#### Running in the background

```bash
sudo -b /usr/local/bin/sys-cache-cleaner.sh
```

<Note>
The above runs the cache cleaner in the current session only; it does not persist across reboots. To have the cache cleaner run across reboots, create a systemd service instead.
</Note>

### Host firewall and Docker bridge subnets

If a default-deny firewall is enabled on the host, allow inbound traffic from the Docker bridge subnets used by VSS. Otherwise, bridge-networked containers cannot reach host-networked services and the affected workflow silently produces no output. See [Bridge-network container cannot reach a VSS service on the host](/vss/appendix/faq#bridge-network-container-cannot-reach-a-vss-service-on-the-host) for diagnostics and the fix.

## Network and Browser Access

The machine running the web browser must be able to reach TCP port `7777` on
the deployment host. This port serves the VSS UI and routes optional web
applications included in the selected service graph, such as Kibana and
Phoenix. The default Build Vision AI deployment does not include Phoenix or
the in-stack VSS Agent; the manual base-profile deployment includes both.

For cloud deployments, configure the instance firewall or security group to allow inbound TCP traffic on port `7777` from the browser client. For local deployments, ensure `http://localhost:7777/` is reachable from the deployment host.

## NGC + Hugging Face API Keys

The credentials you need depend on the images, models, and optional agent
harness selected for the deployment. Standard VSS deployment paths require an
NGC Personal API Key. A Hugging Face token is required only when a selected
model or helper downloads gated or rate-limited weights from Hugging Face. See
the [credential decision table](#credentials-used-by-the-build-vision-ai-skill)
before deploying.

### Create an NVIDIA NGC Account

1. Go to https://ngc.nvidia.com
2. Click **Sign up** if you don't have an account, or **Sign in** if you do
3. Complete the registration process with your email address

### Generate an API Key

1. Once logged in, click on your username in the top right corner
2. Select **Setup** from the dropdown menu
3. Navigate to **API Keys** under the **Keys/Secrets** section
4. Click **Generate API Key**
5. Click **Generate Personal Key** (available at both the top-center and top-right of the page)
6. Provide a descriptive name for your API key (e.g., "VSS Blueprint Development")
7. Select **NGC Catalog** for Key Permissions
8. Click **Generate Personal Key**
9. Copy the generated API key immediately - you won't be able to see it again
10. Store it securely in a password manager or encrypted file

<Note>
Keep your NGC API key secure and never commit it to version control systems.
</Note>

<Info>
The Cosmos3 Reasoner NIM (1.7.0+) requires a **Personal API Key**. Legacy NGC API keys
are not supported and will fail authentication when pulling or running this container.
This applies when you explicitly deploy the standalone Cosmos3 Reasoner NIM.
The default `base` and `search` profiles serve the Cosmos3 model through
RT-VLM and do not start the standalone VLM NIM container. Other NGC images and
model artifacts still require an authorized NGC credential.
</Info>

### Verify Your NGC Access

To verify your NGC key has the correct permissions:

```bash
# Set your NGC API key
export NGC_CLI_API_KEY='your_ngc_api_key'

# Authenticate Docker for gated NIM and other nvcr.io images. The username is
# the literal string $oauthtoken; the password is your NGC Personal API Key.
# Managed VSS images on ghcr.io are public and require no registry login.
printf '%s' "$NGC_CLI_API_KEY" | \
  docker login nvcr.io --username '$oauthtoken' --password-stdin

# Test access to the required resources
ngc registry resource list "nvidia/vss-developer/*"
ngc registry resource list "nvidia/vss-core/*"

# Test access to the required images
ngc registry image list "nvidia/vss-core/*"

# Test access to the required models
ngc registry model list "nvidia/tao/*"
```

If you encounter permission errors, contact NVIDIA support for assistance.

The `Login Succeeded` response verifies NGC Docker registry authentication.
Run this step before the Build Vision AI Skill or any manual
`docker compose up` command that pulls gated NIM or other `nvcr.io` images. A
later `docker compose config --quiet` validates the Compose model and
environment values, but does not contact the registry or validate image
entitlements.

### Hugging Face Access Token

Some optional model selections download weights from
[Hugging Face](https://huggingface.co/). Create a token only when the selected
deployment path identifies `HF_TOKEN` as required. Public downloads can also
be rate limited without a token.

1. Log in to [Hugging Face](https://huggingface.co/)
2. Go to [Access Tokens](https://huggingface.co/settings/tokens) and create a token with **Read** permission
3. Export the token before deploying:

```bash
export HF_TOKEN='hf_your_token_here'
```

<Warning>
The token must have **READ** permission only. Do not commit it to version control.
</Warning>

<Note>
`HF_TOKEN` is also used for gated **Nemotron Omni** model weights and some remote vLLM deploy flows. For **audio-in-video** on the base agent profile, set `ENABLE_AUDIO=true` in the profile `.env` (see inline comments in `dev-profile-base/.env`) and follow [Using Nemotron Omni (audio-enabled remote VLM)](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm#using-nemotron-omni-audio-enabled-vlm) in [Configure the VLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm).
</Note>

### Credentials used by the Build Vision AI Skill

The `vss-build-vision-ai` Skill asks for credentials before it deploys. Which
keys are required depends on model placement and whether you choose the optional
NemoClaw harness.

| Credential | Required when |
| --- | --- |
| `NGC_CLI_API_KEY` | Pulling gated NIM, model, sample-data, and other artifacts from NGC. This is required for the standard deployment paths. Use the same Personal API Key for `docker login nvcr.io`. Managed VSS images on public GHCR require no registry login. |
| `COMPATIBLE_API_KEY` | The NemoClaw harness uses its default remote OpenAI-compatible endpoint, or another public OpenAI-compatible endpoint that requires a bearer token. The default has no built-in key. |
| `NVIDIA_API_KEY` | A selected LLM or VLM is served from `build.nvidia.com`. |
| `HF_TOKEN` | A selected model or helper downloads gated or rate-limited weights from Hugging Face. |

A key for the default NemoClaw Inference Hub endpoint can be created at
[NVIDIA Inference Hub key management](https://inference.nvidia.com/key-management?action=new-key).
Keep it out of chat transcripts and generated build artifacts. Either put the
following assignment in the checkout-root, gitignored `nemoclaw.env` file, or
export it in the shell that starts the coding-agent session:

```bash
COMPATIBLE_API_KEY='your-inference-hub-key'
```

The Skill loads `nemoclaw.env` before harness setup. If you export the variable
instead, restart the coding-agent session from that shell so it inherits the
credential.

A self-hosted OpenAI-compatible harness endpoint that does not require a real
token can use the documented placeholder. Selecting **no harness** requires no
harness credential. These choices do not remove the NGC or model-download
credentials required by the VSS stack itself. The Skill stops before deployment
and identifies any missing credential; it does not silently switch providers.

## VLM Custom Weights

The VSS Blueprint supports using VLM custom weights for specialized use cases. This section explains how to download custom weights from NGC or Hugging Face.

### Download Custom Weights from NGC

If VLM custom weights are available on NGC, you can download them using the NGC CLI:

```bash
# Set your NGC API key if not already set
export NGC_CLI_API_KEY='your_ngc_api_key'

# Download custom weights from NGC
ngc registry model download-version <org>/<team>/<model>:<version>

# Move downloaded custom weights to desired path/folder
mv </downloaded/path/in/ngc/output> </path/to/custom/weights>
```

The weights will be downloaded to a local directory. Note the path to this directory, then set `VLM_CUSTOM_WEIGHTS` in the selected profile's `*-overrides.env` file before deploying (the deployment guides use `user-overrides.env` as an example).

### Download Custom Weights from Hugging Face

To download custom VLM weights from Hugging Face, you can use the `huggingface-cli` tool or Git LFS:

**Using huggingface-cli:**

```bash
# Install Hugging Face CLI if not already installed
pip install -U "huggingface_hub[cli]"

# Login to Hugging Face (required for gated models)
huggingface-cli login

# Create a base directory where the custom weights can be downloaded
mkdir -p </path/to/custom/weights>

# Download a model
huggingface-cli download <model-id> --local-dir </path/to/custom/weights>
```

**Using Git LFS:**

```bash
# Install Git LFS if not already installed
sudo apt install git-lfs
git lfs install

# Clone the model repository
git clone https://huggingface.co/<model-id> </path/to/custom/weights>
```

<Note>
Some Hugging Face models may be gated and require access approval. Visit the model page on Hugging Face and request access if needed. You must also authenticate using `huggingface-cli login` before downloading gated models.
</Note>

### Verify Downloaded Weights

After downloading custom weights, verify the directory structure and contents:

```bash
# List the contents of the weights directory
ls -lh </path/to/custom/weights>
```

Typical VLM weight directories contain:

- Model configuration files (e.g., `config.json`)
- Model weights (e.g., `pytorch_model.bin`, `model.safetensors`, or sharded weights)
- Tokenizer files (e.g., `tokenizer.json`, `tokenizer_config.json`)
- Other metadata files

## Common Installation Issues

When pulling resources from NGC, you may encounter the following issues:

**Error:** `Missing org - If Authenticated, org is also required.`

**Steps to resolve:**

1. Generate an NGC API key with your desired org selected.
2. Ensure that the org you selected in `ngc config set` is the same as the org you selected in the NGC API key generation.

## Appendix: Software Prerequisites Installation Guide

### Install NVIDIA Driver

#### Ubuntu 24.04

NVIDIA Driver version 595.58.03 is required with Ubuntu 24.04.

You can download the driver directly from:
https://www.nvidia.com/en-us/drivers/details/266021/

#### Additional resources

For detailed installation instructions, refer to the official NVIDIA Driver Installation Guide:
https://docs.nvidia.com/datacenter/tesla/driver-installation-guide/index.html

You can also browse drivers for your specific GPU and platform from the NVIDIA Driver Downloads page:
https://www.nvidia.com/Download/index.aspx

<Note>
After installation, verify the driver is correctly installed by running `nvidia-smi` to confirm the driver version and GPU detection.
</Note>

<Note>
**NVIDIA Fabric Manager Requirement**

NVIDIA Fabric Manager is required on systems with multiple GPUs that are connected using NVLink or NVSwitch technology. This typically applies to:

- **NVIDIA DGX systems** — e.g., DGX A100, DGX H100, DGX-2, DGX Station (multi-GPU)
- **HGX platforms** — e.g., H100 4-GPU/8-GPU baseboards
- **NVSwitch-based systems** — servers with NVSwitch fabric (e.g., 8-way HGX B200/H100 with NVSwitch)
- **Multi-GPU servers with NVLink** — OEM systems that use NVLink to connect GPUs rather than PCIe only
- **Datacenter GPUs with NVLink** — hosts with NVIDIA H100, B200, or similar GPUs in an NVLink topology

Fabric Manager is **not required** for:

- Single GPU systems
- Multi-GPU systems without NVLink/NVSwitch (PCIe-only configurations)

For full details, refer to the official NVIDIA Fabric Manager documentation:

- Installation Guide: https://docs.nvidia.com/datacenter/tesla/fabric-manager-user-guide/index.html

Example setup on Ubuntu 24.04. Use Fabric Manager version **595.58.03** so that it matches the installed NVIDIA driver (see [Install NVIDIA Driver](/vss/getting-started/prerequisites#install-nvidia-driver) for driver requirements):

```bash
# Install the Fabric Manager package that matches driver 595.58.03
sudo apt-get update
sudo apt-get install -y nvidia-fabricmanager-595=595.58.03-1ubuntu1

# Enable and start the service
sudo systemctl enable nvidia-fabricmanager
sudo systemctl start nvidia-fabricmanager

# Verify the service is running
sudo systemctl status nvidia-fabricmanager
```

If that exact package revision is unavailable from your apt repository, download and install the matching Debian package directly:

```bash
wget https://developer.download.nvidia.com/compute/cuda/repos/ubuntu2404/x86_64/nvidia-fabricmanager_595.58.03-1ubuntu1_amd64.deb
sudo dpkg -i nvidia-fabricmanager_595.58.03-1ubuntu1_amd64.deb
```

Fabric Manager must match the installed driver version.
</Note>

### Install Docker

Docker version 28.3.3 or later and earlier than 29.5.0 is required. If Docker is
not installed, first install Docker Engine from the
[official Ubuntu apt repository](https://docs.docker.com/engine/install/ubuntu/).
The latest package is not necessarily in the VSS-tested range.

<Note>
Do not install Docker via `snap`. The snap-packaged Docker runs inside a confined sandbox with restricted filesystem access, which can perform differently in the deployment process. Install Docker using the official Docker apt repository as linked above.
</Note>

#### Run docker without sudo

After installation, complete the Linux post-installation steps so that Docker can run without sudo. See [Linux post-installation steps for Docker Engine](https://docs.docker.com/engine/install/linux-postinstall/).

### Pin and configure Docker

From the VSS repository root, run the checked-in setup script before starting
any containers:

```bash
bash deploy/docker/scripts/pin_docker_version.sh
docker version --format '{{.Server.Version}}'
docker info --format '{{.CgroupDriver}}'
```

The script installs the repository's known-good Docker Engine, Compose,
Buildx, and containerd package versions when the installed engine is outside
the tested range. It holds the applicable packages and safely merges the
required `native.cgroupdriver=cgroupfs` setting into `/etc/docker/daemon.json`.
It is idempotent and skips the package change when Docker is already in range.

<Note>
The script uses `sudo`, supports Ubuntu hosts with `apt`, and can restart
Docker. Run it before other containers are started. If the host cannot install
the pinned packages, see the script's error and the
[Docker troubleshooting guidance](/vss/appendix/faq) before changing
`daemon.json` manually.
</Note>

### Install Docker Compose

Docker Compose v2.39.1 or later is required. Docker Compose v2 is typically installed as a plugin with modern Docker installations.

**Check if Docker Compose is already installed and meets the minimum version:**

```bash
docker compose version
```

The default `docker-compose-plugin` package in Ubuntu repositories may provide a version older than v2.39.1.
If the version is missing or too old, select the binary for the host
architecture and install the required version manually:

```bash
case "$(uname -m)" in
  x86_64) COMPOSE_ARCH=x86_64 ;;
  aarch64|arm64) COMPOSE_ARCH=aarch64 ;;
  *) echo "Unsupported architecture: $(uname -m)" >&2; exit 1 ;;
esac

sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -fSL "https://github.com/docker/compose/releases/download/v2.39.1/docker-compose-linux-${COMPOSE_ARCH}" \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
```

**Verify installation:**

```bash
docker compose version
```

<Note>
Docker Compose v2 uses the command `docker compose` (without hyphen) instead of the older `docker-compose` command.
</Note>

### NIM configuration settings

The deployment ships with NIM (NVIDIA Inference Microservice) configuration via environment variables for supported NIMs and GPUs. You can use the default env files, rely on NIM defaults for unsupported GPUs, or supply your own env files at install time.

#### Default configuration

For each supported NIM and GPU, the deployment includes a corresponding env file under `./deploy/docker/services/nim/<nim-name>/`. For example, for the cosmos3-reasoner NIM on an NVIDIA RTX PRO 6000 Blackwell:

```bash
./deploy/docker/services/nim/cosmos3-reasoner/hw-RTXPRO6000BW.env
```

#### Unsupported GPU hardware

For GPU hardware outside the listed profiles, set `HARDWARE_PROFILE=OTHER` in the selected profile's `*-overrides.env` file. The deployment uses a default empty env file and the NIM falls back to its own defaults.

```bash
./deploy/docker/services/nim/cosmos3-reasoner/hw-OTHER.env
```

#### Custom env files at install time

You can define your own env variants for a NIM in the selected profile's `*-overrides.env` file. Set `LLM_ENV_FILE` and/or `VLM_ENV_FILE`; paths can be absolute or relative to `deploy/docker`.

```ini
LLM_ENV_FILE=/path/to/llm.env
VLM_ENV_FILE=/path/to/vlm.env
```
