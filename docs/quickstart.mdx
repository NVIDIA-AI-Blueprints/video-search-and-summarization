## Overview

**Deploy, register a video, get an answer, and generate a report**

This guide will walk you through the steps to deploy a vision agent using the VSS Blueprint. You'll
create a simple vision agent that you can upload videos to, ask questions about the videos, and generate reports.
Afterwards, you can explore adding agent workflows such as video summarization, search, and alerting.

<Note>
**Before you start:** Use `28.3.3 <= Docker Engine < 29.5.0`.
Unsupported Docker Engine versions can fail when pulling some NGC-hosted image tags.
See [Prerequisites](/vss/getting-started/prerequisites) for Docker setup and the supported version band.
</Note>

The following diagram illustrates a conceptual architecture of the base vision agent that you'll deploy:

![Base Vision Agent Architecture](/assets/images/agent-workflows/profile-base-arch.png)

**Key Features of the Base Vision Agent:**

- Upload videos to a video management system and connect the agent to it through the MCP service.
- Report generation tool which utilizes a LLM and VLM to generate reports from the videos.
- Video understanding tool which utilizes a VLM to perform video understanding tasks, such as Q&A.

<Warning>
Agent Skills are released as **Early Access** and are not intended for use in
production environments. Agent Skills for VSS were validated using Claude Opus
5.
</Warning>

## What's being deployed

The exact service set depends on the deployment path:

- **Build Vision AI Skill (default):** VSS UI, VSS Video IO & Storage
  (VIOS), and RT-VLM. RT-VLM serves the Cosmos3 Nano Reasoner model through
  `vss-rtvi-vlm` on port `8018`; there is no separate Cosmos3 Reasoner
  container. The default NemoClaw harness runs on the host outside the Compose
  project and connects the UI chat to its OpenClaw sandbox.
- **[Manual Docker Compose](/vss/getting-started/manual-docker-compose):** The stock base profile adds the in-stack VSS Agent
  to those services. It uses the configured LLM to route requests and
  orchestrate VSS tools.

Build Vision AI removes the in-stack `vss-agent` service whether you select
NemoClaw or no harness. It deploys that service only when your request
explicitly names the in-stack Agent, its REST API, or its chat workflow.

For this walkthrough, select NemoClaw when the Skill asks for a harness.
It runs outside Compose and requires a reachable language model endpoint.
Choose the NVIDIA service, your own OpenAI-compatible endpoint (including a
self-hosted model), or no harness before deployment. The Skill validates the
provider and credentials before provisioning. See [Agent Harnesses](/vss/vision-agent/agent-harnesses)
for alternatives and the standalone NemoClaw setup.

## Prerequisites

Complete the shared Linux, GPU driver, Docker, Container Toolkit, NGC, and
Git LFS requirements in [Prerequisites](/vss/getting-started/prerequisites)
before any platform-specific Spark or Thor steps. Those platform sections add
to the shared requirements.

You can first paste this into the coding agent running on the deployment host:

```text title="Paste into your coding agent"
Check this host against docs/prerequisites.mdx for the VSS base profile.
Report GPU memory, free model/data disk space, Docker and NVIDIA runtime status,
occupied ports, and missing credentials without displaying secret values.
Complete the applicable prerequisites; show any privileged commands that need
my host terminal and tell me when to resume.
```

The checkpoints below mark completion: services ready, sensor registered,
first grounded answer, and a report that opens.

## Download Sample Data and Deployment Package

### Configure NGC Access

<Note>
Before proceeding, ensure that NGC CLI is installed on your system. For installation instructions, see [Install NGC CLI](/vss/getting-started/prerequisites#install-ngc-cli) in the Prerequisites.
</Note>

### Download Sample Data From NGC

For the default Skill-driven path, perform this on the deployment host in a
directory available to the host-side coding agent. The archive creates
`sample-data/dev-profile-sample-data/`; the walkthrough uses
`warehouse_safety_0001.mp4` from that directory. If you instead use the manual
browser upload later on this page from a different machine, copy that file to
the browser machine before uploading it.

This can be done using NGC CLI as documented below, or downloaded from the NGC UI directly.

The `nvidia/vss-developer/dev-profile-sample-data` resource requires authenticated
NGC CLI access with an org selected. If you see `Artifact is not Guest accessible`
or `Missing org`, configure NGC with an API key and org before retrying.
See [Prerequisites](/vss/getting-started/prerequisites) for NGC setup.

```bash title="Run in the host terminal"
# Download sample data
ngc registry resource download-version nvidia/vss-developer/dev-profile-sample-data:3.3.0

EXTRACT_DIR=./sample-data
mkdir -p "${EXTRACT_DIR}"
tar -xf dev-profile-sample-data_v3.3.0/dev-profile-sample-data.tar.gz -C "${EXTRACT_DIR}"

rm -rf dev-profile-sample-data_v3.3.0
```

### Download the Deployment Package

Perform this on the machine where you intend to deploy the agent.

<Note>
**Git LFS required:** The repository uses Git LFS for large files. Install it before cloning or pulling. For example, on Ubuntu/Debian: `sudo apt-get install git-lfs`. On other systems, see [Git LFS installation](https://git-lfs.com/).
</Note>

```bash title="Run in the host terminal"
git clone --branch "${VSS_DOCS_GIT_REF:-develop}" https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization.git
cd video-search-and-summarization
git lfs install
git lfs pull
```

<Note>
The native Docker Compose workflow below uses checkout reference
`${VSS_DOCS_GIT_REF:-develop}`. Keep that reference aligned with the image tags
selected for the documentation build because the Compose file layout is
release-specific.
</Note>

## Prepare your coding agent

Run the coding agent in an environment that can access the VSS Blueprint checkout
and run deployment commands on the target host. For the Docker Compose
quickstart, the deployment host must meet the supported Linux platform,
GPU, Docker, and NVIDIA Container Toolkit requirements in
[Prerequisites](/vss/getting-started/prerequisites). On x86 systems, use Ubuntu
24.04.
The Build Vision AI Skill requires `uv` for mandatory service-graph checks and
helper scripts. Install it before starting the coding agent:

```bash title="Run in the host terminal"
curl -LsSf https://astral.sh/uv/install.sh | sh
```

You can use a remote development environment such as a Brev or Omnistation
sandbox when that environment exposes the required GPU, Docker Engine, network
ports, NGC access, and repository checkout to the coding agent. A Windows or Mac
machine can be used as the browser or coding-agent client, but it is not the
validated Docker Compose deployment host for this quickstart; point the agent at
a supported Linux deployment host instead.

Install the Build Vision AI Skill and the operations Skills before asking the
agent to deploy or operate VSS. From the VSS Blueprint checkout, ask your coding
agent:

```text title="Paste into your coding agent"
Install skills/vss-build-vision-ai and every Skill under skills/operations for
this host. Use the host's standard skills directory. Symlink each Skill folder
rather than copying it so a git pull here keeps the Skills up to date. If a
Skill is already installed and points at this checkout, leave it unchanged.
When done, report every registered path.
```

The standard Skill locations are:

| Host | Skill path |
| --- | --- |
| Codex | `~/.codex/skills/<skill-name>` |
| Claude Code | `~/.claude/skills/<skill-name>` |
| Other `agentskills.io`-compatible hosts | `~/.agents/skills/<skill-name>` |

Before deployment, have the credentials required by your choices available:

| Credential | When the Skill asks for it |
| --- | --- |
| `NGC_CLI_API_KEY` | Standard VSS image, model, and sample-data access. |
| `COMPATIBLE_API_KEY` | A token-protected OpenAI-compatible endpoint. Obtain the key from the endpoint provider. |
| `NVIDIA_API_KEY` | A model served from `build.nvidia.com` or `integrate.api.nvidia.com`. Create a key from [NVIDIA API Keys](https://build.nvidia.com/settings/api-keys). |
| `HF_TOKEN` | Gated or rate-limited model downloads from Hugging Face. |

Authenticate Docker to `nvcr.io` before asking the Skill to deploy. Use the
same NGC Personal API Key that you provide as `NGC_CLI_API_KEY`:

```bash title="Run in the host terminal"
export NGC_CLI_API_KEY='<your-ngc-personal-api-key>'
printf '%s' "$NGC_CLI_API_KEY" | \
  docker login nvcr.io --username '$oauthtoken' --password-stdin
```

For a custom OpenAI-compatible NemoClaw endpoint, obtain the key from the
endpoint provider. Do not paste the key into chat. Store it in the
checkout-root, gitignored `nemoclaw.env` file:

```bash title="Run in the host terminal"
COMPATIBLE_API_KEY='your-provider-api-key'
```

Alternatively, export `COMPATIBLE_API_KEY` in the shell that starts the
coding-agent session. The session must inherit the variable; exporting it later
in another terminal does not update the running agent.

For developer-profile deployments, the Skill asks whether to add a host-side
agent harness. If you select NemoClaw, choose a model provider that is available
from your host. The `build.nvidia.com` provider uses `NVIDIA_API_KEY`; a custom
OpenAI-compatible provider uses `COMPATIBLE_API_KEY`. Select **no harness** to
operate the deployment with the project-local `vss` CLI instead.

A self-hosted endpoint or **no harness** needs no harness key, although the VSS
stack can still require NGC and model-download credentials. See
[Credentials used by the Build Vision AI Skill](/vss/getting-started/prerequisites#credentials-used-by-the-build-vision-ai-skill)
for the complete decision table.

A normal deployment uses the checked-in scripts and generated build files.
No source patch is required. If the agent proposes patching a tracked notebook
or bypassing its build-directory scope to continue, report the exact setup
failure and use a compatible release checkout before retrying.

After installing the Skills and preparing credentials, start a new coding-agent
session from this checkout. Start it from the shell where you exported any
credentials so the session both discovers the Skills and inherits those values.

## Deploy the base profile

Use a coding agent with the [Build Vision AI Skill](/vss/vision-agent/build-vision-ai) to deploy
the validated `base` developer profile. This is the default quickstart path.

```text title="Paste into your coding agent"
Deploy the VSS base profile on this machine.
```

For explicit invocation, use `$vss-build-vision-ai` in Codex or
`/vss-build-vision-ai` in Claude Code. For example, paste into Codex:

```text title="Paste into your coding agent — Codex"
$vss-build-vision-ai Deploy the VSS base profile on this machine with NemoClaw.
```

The agent will:

1. Load `vss-build-vision-ai` and route the request to the stock `base`
   workflow.
2. Confirm prerequisites, credentials, GPU hardware, model placement, and
   host/ingress settings.
3. Ask whether to add a host-side agent harness and, when selected, confirm its
   model provider and required credential.
4. Show the generated deployment plan, including services, model placement,
   endpoints, and readiness checks.
5. Ask for confirmation before starting containers.
6. Deploy the base profile and return the browser-reachable VSS UI URL.

When deployment completes, open the returned URL, typically
`http://<HOST_IP>:7777/`, to use the base vision agent.

<Note>
On edge platforms (DGX Spark, IGX Thor, AGX Thor), a checked-in local
LLM/VLM sharing configuration is available but has not yet been measured on
the target hardware. A remote LLM is recommended for better response time. Add
"with a remote LLM" to the prompt, for example:
*"Deploy the VSS base profile on this DGX-SPARK machine with a remote LLM."*
See
[Configure the LLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-llm) for endpoint options.
</Note>

### Verify the Skill-driven deployment

The default Skill path does not include the in-stack `vss-agent` service, so
do not use port `8000` as its readiness check. Confirm the service set and the
base RT-VLM endpoint instead:

```bash title="Run in the host terminal"
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
curl -fsS "http://<HOST_IP>:8018/v1/health/ready"
curl -fsS "http://<HOST_IP>:30888/vst/api/v1/sensor/version"
curl -fsS "http://<HOST_IP>:7777/"
```

Expect the VSS UI, VIOS/VST services, and `vss-rtvi-vlm`. Do not expect
`vss-agent`, Phoenix, or a local LLM container in the default Skill-generated
service graph. The Skill keeps an LLM only when another selected service needs
it, such as `lvs-server`, or when the harness is explicitly routed to the
build's LLM NIM. It keeps Phoenix when the in-stack Agent is explicitly
requested.

If you selected NemoClaw, use the sandbox name and harness URL returned by the
Skill. Run `nemoclaw <sandbox> gateway-token --quiet` on the deployment host to
get a current token. Use it with the NemoClaw dashboard URL as `/#token=<token>`;
to use chat in the VSS Web UI, enter it in **Connect NemoClaw chat**. Do not
share the token-bearing URL. If you selected no harness, operate the
deployment with the project-local `vss` CLI as directed by the Skill.

#### If the Skill-driven UI Doesn't Load

If the returned UI URL does not open, rerun the readiness commands above and
use `docker ps` to identify any unhealthy container. Check that container's
startup logs with `docker logs <container-name>`; do not use the manual
in-stack Agent check on port `8000` for the default Skill-generated stack.

If the VSS containers are healthy but the NemoClaw dashboard, sandbox, or MCP
tools are unavailable, follow
[NemoClaw Troubleshooting](/vss/vision-agent/agent-harnesses/nemoclaw/troubleshooting).

## Agent Skills walkthrough

Continue from the deployment checkpoint above: connect chat, register the
sample, ask a question, and generate a report. Each prompt below identifies
where it belongs.

This walkthrough is written for developers and users who want to operate VSS
from natural language.

<Note>
Before starting this walkthrough, follow
[Ask the coding agent to install the Skills](/vss/vision-agent/agent-skills#step-2-ask-the-coding-agent-to-install-the-skills)
if you have not already completed [Prepare your coding agent](#prepare-your-coding-agent),
then start a new coding-agent session so all four Skills below are discovered.
If Build Vision AI provisioned NemoClaw, run the operational steps in the
NemoClaw session; its Skills are installed inside that sandbox, not back into
the original coding-agent session. Also confirm your host meets the
[Prerequisites](/vss/getting-started/prerequisites).
</Note>

The base profile journey exercises four skills:

| Quickstart step | Skill | What it does |
| --- | --- | --- |
| Deploy the base profile | `vss-build-vision-ai` | Selects the stock `base` workflow, confirms deployment context, and brings up the base stack. |
| Upload a video | `vss-manage-video-io-storage` | Ingests files and manages sensors, snapshots, and clips via VIOS/VST. |
| Ask questions | `vss-ask-video` | Routes through conversation context and memory first, then uses `vss vlm run` only for an exact, grounded visual inspection. |
| Generate a report | `vss-generate-video-report` | Generates a report through Mode A (VIOS clip + direct VLM call) or Mode B (incident query via analytics), depending on the prompt. |
| Tear down | `vss-build-vision-ai` | Tears down the deployed build and cleans up profile-specific runtime state when needed. |

Start with [Deploy the base profile](#deploy-the-base-profile) above, then
continue with the sandbox handoff and video steps below.

### Connect NemoClaw and transfer the sample

At the end of deployment, have the Skill return this handoff together:

| Item | Value to use |
| --- | --- |
| Sandbox name | The exact name created by the Skill |
| VSS UI and NemoClaw dashboard | URLs returned after readiness checks |
| Chat connection | Obtain a token with the command below, then use **Connect NemoClaw chat** in the VSS UI |
| Host file | Absolute path to `sample-data/dev-profile-sample-data/warehouse_safety_0001.mp4` |
| Sandbox file | `/sandbox/warehouse_safety_0001.mp4` |

```bash title="Run in the host terminal"
nemoclaw <sandbox-name> gateway-token --quiet
nemoclaw <sandbox-name> upload \
  <absolute-host-path>/sample-data/dev-profile-sample-data/warehouse_safety_0001.mp4 \
  /sandbox/
```

Use the token locally in the dashboard or VSS connection dialog. Keep it out
of shared URLs and chat messages. Run operational prompts in NemoClaw chat
once the connection is established. With no harness, use the host coding-agent
session and its host file path instead.

**Deployment checkpoint:** all selected services are ready, and the chosen
chat session responds. An unavailable harness is a setup failure even if the
vision services are running.

### Upload a video and manage storage

The Skill reads the video from the filesystem of the agent session that runs
it. For a coding agent running directly on the deployment host, provide the
absolute host path:

**Example prompts**

```text title="Paste into your coding agent"
Upload <absolute-path>/sample-data/dev-profile-sample-data/warehouse_safety_0001.mp4 to VSS.
List all available sensors.
Take a snapshot of warehouse_safety_0001 at 0:05.
```

After [transferring the video](#connect-nemoclaw-and-transfer-the-sample),
ask in NemoClaw chat:

```text title="Paste into NemoClaw chat"
Upload /sandbox/warehouse_safety_0001.mp4 to VSS.
```

**What the agent does:**

1. Loads the `vss-manage-video-io-storage` skill, which drives the Video IO &
   Storage (VIOS / VST) microservices.
2. For an upload, it uploads the file via HTTP PUT to VST and confirms a sensor
   is registered for it.
3. For "list sensors," it queries the VIOS sensor list and returns the
   registered sensors and file names.
4. For snapshots, clips, or recording timelines, it calls the matching VIOS
   endpoint at the requested timestamp/range and returns the artifact.

**Registration checkpoint:** the upload returns a registered sensor named
`warehouse_safety_0001`; listing sensors shows that same name. A stored file
without a sensor record is not a completed registration.

### Ask questions about the video

**Example prompts**

```text title="Paste into NemoClaw chat"
Is the worker in warehouse_safety_0001 wearing PPE?
```

**What the agent does:**

1. Loads the `vss-ask-video` skill.
2. Checks hot conversation context, agent Markdown memory, and structured VSS
   memory before requesting new visual inference.
3. Uses `vss memory introspect` when introspection is configured. For an exact
   sensor and time window, pre-resolved media URL, or local file that needs a
   fresh visual inspection, it uses the project-local `vss vlm run` command.
4. Returns a grounded answer with the available job or record handles and
   reports CLI failures by exit code instead of falling back to raw REST.

<Note>
The Skill does not call an OpenAI-compatible `/chat/completions` endpoint or the
VSS agent's `/generate` endpoint directly. The `vss` CLI owns endpoint discovery,
media resolution, memory access, and any underlying VLM request.
</Note>

**Answer checkpoint:** the response describes observed content and includes a
video timestamp or evidence handle. Report any CLI or backend failure before
continuing.

### Generate a report

**Example prompt**

```text title="Paste into NemoClaw chat"
Generate a report for warehouse_safety_0001.
```

**What the agent does:**

1. Loads the `vss-generate-video-report` skill.
2. Resolves the clip URL through `vss-manage-video-io-storage`, calls the selected VLM, and renders the markdown report from that output. (Does **not** use the VSS agent `/generate` endpoint.)
3. Returns the rendered markdown report to the user.

**Report checkpoint:** open the returned Markdown report and any requested PDF,
snapshot, or clip links. Confirm they correspond to `warehouse_safety_0001`.

### Tear down the deployment

**Example prompt**

```text title="Paste into NemoClaw chat"
Tear down the VSS deployment.
```

**What the agent does:**

1. Loads the `vss-build-vision-ai` skill and runs the teardown flow for the
   deployed build.
2. When switching profiles, it also clears stale data volumes before any
   redeploy.
