## Overview

**Deploy a vision agent in 10 minutes**

This guide will walk you through the steps to deploy a vision agent using the VSS Blueprint. You'll
create a simple vision agent that you can upload videos to, ask questions about the videos, and generate reports.
Afterwards, you can explore adding agent workflows such as video summarization, search, and alerting.

<Note>
**Before you start:** Use `28.3.3 <= Docker Engine < 29.5.0`.
Unsupported Docker Engine versions can fail when pulling some NGC-hosted image tags.
See [Prerequisites](/vss/getting-started/prerequisites) for Docker setup and the supported version band.
</Note>

The following diagram illustrates a conceptual architecture of the base vision agent that you'll deploy:

![Base Vision Agent Architecture](/assets/images/agent-workflows/profile-base-arch.png)

**Key Features of the Base Vision Agent:**

- Upload videos to a video management system and connect the agent to it through the MCP service.
- Report generation tool which utilizes a LLM and VLM to generate reports from the videos.
- Video understanding tool which utilizes a VLM to perform video understanding tasks, such as Q&A.

## What's being deployed

The exact service set depends on the deployment path:

- **Build Vision AI Skill (default):** VSS Agent UI, VSS Video IO & Storage
  (VIOS), Phoenix, RT-VLM, and a local Nemotron LLM NIM when local model
  placement is selected. RT-VLM serves the Cosmos3 Nano Reasoner model through
  `vss-rtvi-vlm` on port `8018`; there is no separate Cosmos3 Reasoner
  container. The default NemoClaw harness runs on the host outside the Compose
  project and connects the UI chat to its OpenClaw sandbox.
- **Manual Docker Compose:** The stock base profile adds the in-stack VSS Agent
  to those services. It uses the configured LLM to route requests and
  orchestrate VSS tools.

Build Vision AI removes the in-stack `vss-agent` service whether you select
NemoClaw or no harness. It deploys that service only when your request
explicitly names the in-stack Agent, its REST API, or its chat workflow.

## Agent Harness Options

For Build Vision AI deployments, NemoClaw is the default and recommended agent
harness for interacting with VSS.
The underlying VSS microservices (Video Analytics MCP, VSS Orchestrator MCP,
VST/VIOS, and Video Analytics API) are framework-agnostic, so you can also drive
them through direct MCP or REST integrations. The table below compares the
supported options.

| Harness | What it is | Pros | Cons |
| --- | --- | --- | --- |
| **NemoClaw (OpenClaw sandbox, Build Vision AI default)** | An agent sandbox with a chat UI that drives VSS through the [VSS Orchestrator MCP server](/vss/vision-agent/agent-harnesses/nemoclaw/vss-orchestrator-mcp) (port `9988`). Bundled with VSS skills and a policy preset; installed via the `deploy_nemoclaw.ipynb` and `deploy_vss_orchestrator.ipynb` notebooks. See [NemoClaw](/vss/vision-agent/agent-harnesses/nemoclaw). | Natural-language *operations* on top of VSS (deploy profiles, fetch logs, inspect containers); guided host setup; safety prompts before destructive actions; policy-controlled skills. | Focused on deploying and operating VSS rather than building bespoke video analytics agents; requires the orchestrator MCP server to be running on the host. |
| **Direct MCP client** (BYO agent) | Any MCP-compatible LLM client (e.g., Claude Desktop, OpenAI Agents SDK with MCP, custom Python) connecting to VSS's MCP servers: [Video Analytics MCP](/vss/system-components/middleware/api-gateway-mcp/video-analytics-mcp) (port `9901`) and/or [VSS Orchestrator MCP](/vss/vision-agent/agent-harnesses/nemoclaw/vss-orchestrator-mcp) (port `9988`). | Maximum flexibility — bring any model, framework, or language; lightweight; easy to embed into existing agent stacks; reuses VSS's existing tool surface without running the full VSS Agent. | You implement orchestration, retries, multi-turn memory, and streaming yourself; no out-of-the-box Phoenix tracing or Reference UI integration. |
| **Direct REST API** (no LLM in the loop) | Custom HTTP client calling the [Video Analytics API](/vss/system-components/middleware/api-gateway-mcp/video-analytics-api/video-analytics-api-reference) (port `8081`), VST/VIOS APIs (port `30888`), or the VSS Agent's own REST endpoints (`/generate`, `/chat`, `/api/v1/videos` on port `8000`). | No agent runtime required; lowest latency; ideal for embedding VSS into existing applications, dashboards, or batch pipelines; deterministic. | No reasoning or tool routing — caller must know exactly which API to invoke; not suitable for natural-language workflows. |

<Note>
When you deploy with Build Vision AI, NemoClaw runs on the host outside the
Docker Compose project, and the in-stack VSS Agent is omitted unless the request
explicitly names it. The manual Docker Compose base-profile commands later on
this page use the stock `COMPOSE_PROFILES` and still deploy the NAT-based VSS
Agent.
</Note>

## Download Sample Data and Deployment Package

### Configure NGC Access

<Note>
Before proceeding, ensure that NGC CLI is installed on your system. For installation instructions, see [Install NGC CLI](/vss/getting-started/prerequisites#install-ngc-cli) in the Prerequisites.
</Note>

### Download Sample Data From NGC

Perform this on the machine from which you may use the web-browser.

This can be done using NGC CLI as documented below, or downloaded from the NGC UI directly.

The `nvidia/vss-developer/dev-profile-sample-data` resource requires authenticated
NGC CLI access with an org selected. If you see `Artifact is not Guest accessible`
or `Missing org`, configure NGC with an API key and org before retrying.
See [Prerequisites](/vss/getting-started/prerequisites) for NGC setup.

```bash
# Download sample data
ngc registry resource download-version nvidia/vss-developer/dev-profile-sample-data:3.2.0

EXTRACT_DIR=./sample-data
mkdir -p "${EXTRACT_DIR}"
tar -xf dev-profile-sample-data_v3.2.0/dev-profile-sample-data.tar.gz -C "${EXTRACT_DIR}"

rm -rf dev-profile-sample-data_v3.2.0
```

### Download the Deployment Package

Perform this on the machine where you intend to deploy the agent.

<Note>
**Git LFS required:** The repository uses Git LFS for large files. Install it before cloning or pulling. For example, on Ubuntu/Debian: `sudo apt-get install git-lfs`. On other systems, see [Git LFS installation](https://git-lfs.com/).
</Note>

```bash
git clone https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization.git
cd video-search-and-summarization
git checkout tags/v3.3.0
git lfs install
git lfs pull
```

## Prepare your coding agent

Run the coding agent in an environment that can access the VSS Blueprint checkout
and run deployment commands on the target host. For the Docker Compose
quickstart, the deployment host must meet the supported Linux platform,
GPU, Docker, and NVIDIA Container Toolkit requirements in
[Prerequisites](/vss/getting-started/prerequisites). On x86 systems, use the
Ubuntu version listed there; do not substitute a different release.
The Build Vision AI Skill also requires `uv` for mandatory service-graph checks
and helper scripts. Without it, deployment can fail even when the remaining
host checks pass.

You can use a remote development environment such as a Brev or Omnistation
sandbox when that environment exposes the required GPU, Docker Engine, network
ports, NGC access, and repository checkout to the coding agent. A Windows or Mac
machine can be used as the browser or coding-agent client, but it is not the
validated Docker Compose deployment host for this quickstart; point the agent at
a supported Linux deployment host instead.

Install the Build Vision AI Skill and the operations Skills before asking the
agent to deploy or operate VSS. From the VSS Blueprint checkout, ask your coding
agent:

```text title="Install the VSS Skills"
Install skills/vss-build-vision-ai and every Skill under skills/operations for
this host. Use the host's standard skills directory. Symlink each Skill folder
rather than copying it so a git pull here keeps the Skills up to date. If a
Skill is already installed and points at this checkout, leave it unchanged.
When done, report every registered path.
```

The standard Skill locations are:

| Host | Skill path |
| --- | --- |
| Codex | `~/.codex/skills/<skill-name>` |
| Claude Code | `~/.claude/skills/<skill-name>` |
| Other `agentskills.io`-compatible hosts | `~/.agents/skills/<skill-name>` |

After installation, start a new coding-agent session from this checkout so the
agent discovers the deployment and operations Skills.

Before deployment, have the credentials required by your choices available:

| Credential | When the Skill asks for it |
| --- | --- |
| `NGC_CLI_API_KEY` | Standard VSS image, model, and sample-data access. |
| `COMPATIBLE_API_KEY` | The default NemoClaw remote endpoint, or another token-protected OpenAI-compatible endpoint. There is no default key. |
| `NVIDIA_API_KEY` | A model served from `build.nvidia.com`. |
| `HF_TOKEN` | Gated or rate-limited model downloads from Hugging Face. |

A self-hosted endpoint or **no harness** needs no harness key, although the VSS
stack can still require NGC and model-download credentials. See
[Credentials used by the Build Vision AI Skill](/vss/getting-started/prerequisites#credentials-used-by-the-build-vision-ai-skill)
for the complete decision table.

## Deploy the base profile

Use a coding agent with the [Build Vision AI Skill](/vss/vision-agent/build-vision-ai) to deploy
the validated `base` developer profile. This is the default quickstart path.

```text title="Example prompt"
Use the vss-build-vision-ai skill to deploy the VSS base profile on this machine.
```

The agent will:

1. Load `vss-build-vision-ai` and route the request to the stock `base`
   workflow.
2. Confirm prerequisites, credentials, GPU hardware, model placement, and
   host/ingress settings.
3. Show the generated deployment plan, including services, model placement,
   endpoints, and readiness checks.
4. Ask for confirmation before starting containers.
5. Deploy the base profile and return the browser-reachable VSS UI URL.

When deployment completes, open the returned URL, typically
`http://<HOST_IP>:7777/`, to use the base vision agent.

<Note>
On edge platforms (DGX Spark, IGX Thor, AGX Thor), local LLM/VLM sharing is
supported, but a remote LLM is recommended for better response time. Add
"with a remote LLM" to the prompt, for example:
*"Use the vss-build-vision-ai skill to deploy the VSS base profile on this
DGX-SPARK machine with a remote LLM."* See
[Configure the LLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-llm) for endpoint options.
</Note>

### Verify the Skill-driven deployment

The default Skill path does not include the in-stack `vss-agent` service, so
do not use port `8000` as its readiness check. Confirm the service set and the
base RT-VLM endpoint instead:

```bash
docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
curl -fsS "http://<HOST_IP>:8018/v1/health/ready"
curl -fsS "http://<HOST_IP>:7777/"
```

Expect the VSS UI, VIOS/VST services, `vss-rtvi-vlm`, Phoenix, and the local
Nemotron LLM container when local LLM placement was selected. Do not expect a
`vss-agent` container. For a local LLM, also verify its readiness endpoint:

```bash
curl -fsS "http://<HOST_IP>:30081/v1/health/ready"
```

If you selected NemoClaw, use the sandbox name and harness URL returned by the
Skill. The setup log contains the authenticated dashboard URL; do not copy or
share its token-bearing fragment. If you selected no harness, operate the
deployment with the project-local `vss` CLI as directed by the Skill.

## Manual deployment options

Use this section when you want to run the deployment script yourself or customize
the base profile from the command line.

### Docker Compose deployment

<Note>
- Set the NGC CLI API key and Hugging Face token (`HF_TOKEN`), then run the deploy commands for your GPU type. See [NGC + Hugging Face API Keys](/vss/getting-started/prerequisites#ngc-hugging-face-api-keys).
- Refer to [Configure the LLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-llm) and [Configure the VLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm) for all LLM and VLM (local and remote) configuration options.
- For **Nemotron Omni** video+audio with a remote VLM, set `ENABLE_AUDIO=true` and follow [Using Nemotron Omni (audio-enabled remote VLM)](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm#using-nemotron-omni-audio-enabled-vlm) in [Configure the VLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm).
- For advanced settings and Agent Customization, edit the profile `user-overrides.env`.
</Note>

```bash
# Set NGC CLI API key and Hugging Face access token (HF_TOKEN)
export NGC_CLI_API_KEY='<your-ngc-api-key>'
export HF_TOKEN='<hf-token>'

# Authenticate Docker for gated NIM and other nvcr.io images. The managed VSS
# images on ghcr.io are public and do not require a registry login.
printf '%s' "$NGC_CLI_API_KEY" | \
  docker login nvcr.io --username '$oauthtoken' --password-stdin

```

See [Configuration](/vss/system-components/configuration) for common variables,
valid values, defaults, and env-file precedence. The complete profile-specific
template is
`deploy/docker/developer-profiles/dev-profile-base/overrides.env`.

Select a hardware tab, then a deployment mode. **Shared GPU** runs the LLM and VLM NIMs on the same GPU; **Dedicated GPU** assigns each model its own GPU (via `LLM_DEVICE_ID` and `VLM_DEVICE_ID`).

`overrides.env` is the checked-in template. From `deploy/docker`, copy it to any
filename matching `*-overrides.env` before selecting a layout. Files matching
that pattern are ignored by Git so local settings and credentials are not
committed. The commands below use `user-overrides.env` as a concrete example;
if you choose another name, use it consistently in every `--env-file` argument.
Repeat the copy only when you want to discard prior layout changes:

```bash
PROFILE=base
cp "developer-profiles/dev-profile-${PROFILE}/overrides.env" \
  "developer-profiles/dev-profile-${PROFILE}/user-overrides.env"
```

For each layout below, update the shown values in
`deploy/docker/developer-profiles/dev-profile-base/user-overrides.env`.
After completing the host-path preparation and one hardware layout, use the
startup commands following the layout tabs.

**Environment-variable overrides:** In `deploy/docker/developer-profiles/dev-profile-base/user-overrides.env`, update existing values in place; add a variable only when it is absent. `COMPOSE_PROFILES` is derived from values above it, so appending duplicate model-mode or model-slug variables can select the wrong services.

On GB300, DGX Spark, and other SBSA hosts, export
`VSS_CONTAINER_TAG_SUFFIX=-sbsa` in the shell before running Compose. This
appends `-sbsa` to the managed RT-CV, RT-Embed, RT-VLM, and Video Summarization
image tags while preserving the shared `VSS_CONTAINER_TAG` release channel. Do
not put the suffix in `user-overrides.env`: `containers.env` derives the image
tags before later env files are read.

**Host-path and service-address overrides (all hardware profiles):**

- `VSS_APPS_DIR`: Absolute path to this repository's `deploy/docker` directory.
- `VSS_DATA_DIR`: Absolute writable host directory for downloaded models, videos, and service data.
- `HOST_IP`: IP address or hostname that clients use to reach services on this VSS host. Set it to an address reachable by the intended clients.
- `EXTERNAL_IP`: Address VSS puts in externally reachable service URLs. It defaults to `${HOST_IP}`; on a cloud host or when clients connect from outside the host network, set it to the instance's public address or external hostname.


Set these required placeholder values in the existing assignments:

```ini
VSS_APPS_DIR=/absolute/path/to/video-search-and-summarization/deploy/docker
VSS_DATA_DIR=/absolute/path/to/vss-apps-data
HOST_IP=<reachable-host-ip-or-name>
```

**Prepare host data directories before starting Compose.** Use the same `VSS_DATA_DIR` (and, for Alerts, `VSS_APPS_DIR`) values set above:

```bash
VSS_DATA_DIR=/absolute/path/to/vss-apps-data
mkdir -p \
  "$VSS_DATA_DIR/data_log/analytics_cache" \
  "$VSS_DATA_DIR/data_log/calibration_toolkit" \
  "$VSS_DATA_DIR/data_log/elastic/data" \
  "$VSS_DATA_DIR/data_log/elastic/logs" \
  "$VSS_DATA_DIR/data_log/kafka" \
  "$VSS_DATA_DIR/data_log/redis/data" \
  "$VSS_DATA_DIR/data_log/redis/log" \
  "$VSS_DATA_DIR/agent_eval/dataset" \
  "$VSS_DATA_DIR/agent_eval/results"
chmod -R 777 "$VSS_DATA_DIR/data_log" "$VSS_DATA_DIR/agent_eval"
```

Docker Compose downloads the required containers from the configured GHCR and NGC registries and starts the agent. Depending on
your network speed, this may take a few minutes.

<Note>
When using a remote VLM of model-type `nim` (not `openai`), see [How does a remote `nim` VLM access videos?](/vss/appendix/faq#how-does-a-remote-nim-vlm-access-videos) for access requirements.
</Note>

<Note>
**Switch Agent Workflows:** Prefer `deploy/docker/scripts/dev-profile.sh`. That helper writes `generated.env` and applies profile-specific flags. If you run `docker compose` directly, use the matching `developer-profiles/dev-profile-<profile>/.env` plus `user-overrides.env` (or `generated.env` after the helper has run). Later `--env-file` values win.

Switch profiles by changing the `dev-profile-<profile>` directory, not by setting `MODE` to `base`/`lvs`/`search`/`alerts`. Those names are profile directories. For the **alerts** profile only, `MODE` is:

- [Alert Verification Workflow](/vss/vision-agent/agent-workflows/alert-verification#step-1-deploy-the-agent) — `MODE=2d_cv`
- [Real-Time Alert Workflow](/vss/vision-agent/agent-workflows/real-time-alerts#step-1-deploy-the-agent) — `MODE=2d_vlm`
</Note>

### Verify the manual in-stack Agent deployment

Once the deployment is complete, check that all the containers are running and healthy:

```bash
docker ps
```

Once all the containers are running, you can access the agent UI at `http://<HOST_IP>:7777/`.

#### If the UI Doesn't Load

If `http://<HOST_IP>:7777/` does not open, run these checks before redeploying:

1. Check the VSS Agent health endpoint:

   ```bash
   curl -fsS "http://<HOST_IP>:8000/health"
   ```

2. Confirm the expected base-profile containers are running and healthy:

   ```bash
   docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
   ```

   Look for the VSS Agent, VSS Agent UI, VIOS/VST, Nemotron LLM,
   `vss-rtvi-vlm`, and Phoenix containers.

3. If containers are unhealthy or certain services are unresponsive, check the corresponding
   container logs for startup, or configuration errors.

4. If containers are healthy but the UI or workflow is still unavailable, check
   whether the host firewall is blocking container-to-host traffic. See
   [Bridge-network container cannot reach a VSS service on the host](/vss/appendix/faq#bridge-network-container-cannot-reach-a-vss-service-on-the-host).

5. If the `vss-rtvi-vlm` container stopped or crashed **in shared GPU
   mode**, redeploy the full blueprint instead of restarting only that container.
   With dedicated GPUs, restarting the container is sufficient. See
   [Agent Known Issues](/vss/vision-agent/vss-agents/agent-known-issues).

For the recommended agent-guided deployment path, see
[Deploy the base profile](/vss/getting-started/quickstart#deploy-the-base-profile).

## Agent Skills walkthrough

The default quickstart deploys the base profile with a coding agent and the
Build Vision AI Skill. This section expands that same agent-driven journey —
deploy, upload, ask, report, tear down — and documents the **example prompt** you
give the agent and **what the agent does** in response.

This walkthrough is written for developers and users who want to operate VSS
from natural language.

<Note>
Before starting this walkthrough, follow
[Ask the coding agent to install the Skills](/vss/vision-agent/agent-skills#step-2-ask-the-coding-agent-to-install-the-skills)
if you have not already completed [Prepare your coding agent](#prepare-your-coding-agent),
then start a new coding-agent session so all four Skills below are discovered.
If Build Vision AI provisioned NemoClaw, run the operational steps in the
NemoClaw session; its Skills are installed inside that sandbox, not back into
the original coding-agent session. Also confirm your host meets the
[Prerequisites](/vss/getting-started/prerequisites).
</Note>

The base profile journey exercises four skills:

| Quickstart step | Skill | What it does |
| --- | --- | --- |
| Deploy the base profile | `vss-build-vision-ai` | Selects the stock `base` workflow, confirms deployment context, and brings up the base stack. |
| Upload a video | `vss-manage-video-io-storage` | Ingests files and manages sensors, snapshots, and clips via VIOS/VST. |
| Ask questions | `vss-ask-video` | Routes through conversation context and memory first, then uses `vss vlm run` only for an exact, grounded visual inspection. |
| Generate a report | `vss-generate-video-report` | Generates a report through Mode A (VIOS clip + direct VLM call) or Mode B (incident query via analytics), depending on the prompt. |
| Tear down | `vss-build-vision-ai` | Tears down the deployed build and cleans up profile-specific runtime state when needed. |

### Deploy with Build Vision AI

**Example prompts**

```text title="Example prompts"
Use the vss-build-vision-ai skill to deploy the VSS base profile on this machine.
Use the vss-build-vision-ai skill to deploy VSS base with a remote LLM at https://integrate.api.nvidia.com.
```

<Note>
On edge platforms (DGX Spark, IGX Thor, AGX Thor), local LLM/VLM sharing is
supported, but a remote LLM is recommended for better response time — add
"with a remote LLM" to the prompt (for example, *"Deploy the VSS base profile
on this DGX-SPARK machine with a remote LLM."*). See
[Configure the LLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-llm) for endpoint options.
</Note>

The deploy skill chooses the `<platform>` and `<mode>` to match your host,
as documented in [Development Profile GPU Requirements](/vss/getting-started/prerequisites#development-profile-gpu-requirements).

**What the agent does:**

1. Loads the `vss-build-vision-ai` skill and selects the stock `base`
   workflow.
2. Collects the required deployment context (repo path, GPU hardware,
   local/remote LLM-VLM mode, credentials, and host/ingress settings) and asks
   for anything missing.
3. Runs pre-flight checks and credential validation before deployment.
4. Generates and validates the base deployment plan, then shows a review
   summary (services, model placement, and key endpoints).
5. Waits for your confirmation before starting containers.
6. Deploys with `up -d` and waits for readiness gates (container state and
   core health checks).
7. Returns a browser-reachable ingress URL (for example
   `http://<HOST_IP>:7777/`) for opening the UI.

The base defaults are the `nvidia/nemotron-3.5-lightning-30b-a3b` LLM NIM
(port `30081`) and the `nvidia/cosmos3-nano-reasoner` model served through
RT-VLM in the `vss-rtvi-vlm` container (port `8018`,
`VLM_MODEL_TYPE=rtvi`). To use a different model or a remote endpoint, name it
in the prompt and the agent sets `LLM_MODE` / `VLM_MODE` accordingly.

### Upload a video and manage storage

**Example prompts**

```text title="Example prompts"
Upload the sample video warehouse_safety_0001.mp4 from the sample-data directory to VSS.
List all available sensors.
Take a snapshot of warehouse_safety_0001 at 0:05.
```

**What the agent does:**

1. Loads the `vss-manage-video-io-storage` skill, which drives the Video IO &
   Storage (VIOS / VST) microservices.
2. For an upload, it uploads the file via HTTP PUT to VST and confirms a sensor
   is registered for it.
3. For "list sensors," it queries the VIOS sensor list and returns the
   registered sensors and file names.
4. For snapshots, clips, or recording timelines, it calls the matching VIOS
   endpoint at the requested timestamp/range and returns the artifact.

### Ask questions about the video

**Example prompts**

```text title="Example prompts"
Is the worker in warehouse_safety_0001 wearing PPE?
```

**What the agent does:**

1. Loads the `vss-ask-video` skill.
2. Checks hot conversation context, agent Markdown memory, and structured VSS
   memory before requesting new visual inference.
3. Uses `vss memory introspect` when introspection is configured. For an exact
   sensor and time window, pre-resolved media URL, or local file that needs a
   fresh visual inspection, it uses the project-local `vss vlm run` command.
4. Returns a grounded answer with the available job or record handles and
   reports CLI failures by exit code instead of falling back to raw REST.

<Note>
The Skill does not call an OpenAI-compatible `/chat/completions` endpoint or the
VSS agent's `/generate` endpoint directly. The `vss` CLI owns endpoint discovery,
media resolution, memory access, and any underlying VLM request.
</Note>

### Generate a report

**Example prompt**

```text title="Example prompt"
Generate a report for warehouse_safety_0001.
```

**What the agent does:**

1. Loads the `vss-generate-video-report` skill.
2. Resolves the clip URL through `vss-manage-video-io-storage`, calls the selected VLM, and renders the markdown report from that output. (Does **not** use the VSS agent `/generate` endpoint.)
3. Returns the rendered markdown report to the user.

### Tear down the deployment

**Example prompt**

```text title="Example prompt"
Tear down the VSS deployment.
```

**What the agent does:**

1. Loads the `vss-build-vision-ai` skill and runs the teardown flow for the
   deployed build.
2. When switching profiles, it also clears stale data volumes before any
   redeploy.
