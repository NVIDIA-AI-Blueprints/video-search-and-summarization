This page provides API reference for the Alert Verification microservice.

## Overview

The Alert Verification API provides HTTP endpoints for alert and incident submission. It enables external systems to submit alerts for processing through the Alerts Microservice.

## Base URL

The API is available at:

* **REST API**: `http://<host>:<port>/api/v1`

## Authentication

The Alert Verification API does not currently require authentication. Requests are accepted without an `Authorization` header.

<Note>
When deployed behind an API Gateway, authentication may be enforced at the gateway level. Consult your deployment configuration for details.
</Note>

## Realtime incident consolidation

The Real-Time VLM (RT-VLM) microservice evaluates a live stream chunk by chunk. While one physical event stays visible, every chunk can produce a confirmed incident, so a single intrusion that lasts a few minutes is stored as several incident documents. Consolidation groups consecutive confirmed chunks from the same camera and alert category into one event at the time the incidents are read.

Consolidation is:

- **Opt-in per request.** Pass `consolidate=true` on `GET /api/v1/realtime/incidents`. Omitting the parameter, or setting it to `false`, returns the raw incident documents exactly as before.
- **Read-time only.** Grouping happens while the query runs. The raw Elasticsearch documents are never modified or deleted, and the raw view remains available for the same time window.
- **API-only.** The current VSS UI does not use this option. Alerts are not deduplicated automatically in the UI.

### Request

`GET /api/v1/realtime/incidents`

| Parameter | Required | Description |
| --- | --- | --- |
| `consolidate` | No | `true` returns consolidated events. Omitted or `false` returns raw incident documents. |
| `start_time` | With `consolidate=true` | Start of the time window in ISO-8601 format, for example `2026-09-04T10:00:00Z`. |
| `end_time` | With `consolidate=true` | End of the time window in ISO-8601 format. |
| `sensor_id` | No | Restrict the result to one camera. Matches the stored `sensorId`, which is the sensor name given when the rule was created. A rule created without a sensor name stores the VIOS stream UUID instead. |
| `category` | No | Restrict the result to one alert category. |
| `limit` | No | Page size, 1 to 1000, default 100. In the consolidated view this counts events. |
| `offset` | No | Number of items to skip, default 0. In the consolidated view this counts events. |

A consolidated query requires both `start_time` and `end_time`. If either is missing, the service returns HTTP 400 with `"error": "validation_failed"`. Grouping runs over the whole window before pagination is applied, so an event is never split across pages.

<Note>
Provide `sensor_id` and `category` when you want the events for one camera or one alert category. Without them the response contains events for every camera and category in the window. Chunks from different cameras or categories are never merged with each other.
</Note>

Consolidated query:

```bash
curl -sfG "http://<host>:9080/api/v1/realtime/incidents" \
  --data-urlencode "sensor_id=warehouse_sample" \
  --data-urlencode "category=intrusion" \
  --data-urlencode "start_time=2026-09-04T10:00:00Z" \
  --data-urlencode "end_time=2026-09-04T10:30:00Z" \
  --data-urlencode "consolidate=true" \
  --data-urlencode "limit=100"
```

Raw equivalent for the same window:

```bash
curl -sfG "http://<host>:9080/api/v1/realtime/incidents" \
  --data-urlencode "sensor_id=warehouse_sample" \
  --data-urlencode "start_time=2026-09-04T10:00:00Z" \
  --data-urlencode "end_time=2026-09-04T10:30:00Z" \
  --data-urlencode "consolidate=false"
```

Use the same window for both queries when you compare them. Without a window the raw view counts the whole incident history.

### Response

Both views return the same envelope: `status`, `incidents`, `count`, `total`, and `timestamp`. The consolidated view adds `truncated`.

| Field | Raw view | Consolidated view |
| --- | --- | --- |
| `incidents` | Raw incident documents, newest first. | Consolidated events in the NvSchema incident shape. |
| `count` | Number of documents on this page. | Number of events on this page. |
| `total` | Number of raw documents matching the query, as reported by Elasticsearch. Exact below 10,000 and capped at 10,000 above that. | Number of consolidated events in the requested window. This is not the number of raw chunks. It is exact when `truncated` is `false`; when `truncated` is `true` it counts only the events built from the scanned chunks. |
| `truncated` | Not present (the schema default is `false`). | `true` when the window matched more raw chunks than the internal scan cap. See below. |

Each consolidated event:

- Has a synthetic `Id` with the prefix `evt-`, derived from its chunks. The event is not a stored document and cannot be fetched by this ID.
- Starts at the first chunk's `timestamp` and ends at the last chunk's `end`.
- Lists the IDs of the underlying raw incidents in `chunk_ids`.
- Carries `info.isConsolidated` set to `"true"` and `info.chunkCount` with the number of combined chunks. `info.chunkIdxRange` gives the lowest and highest chunk index among the merged chunks, for example `"41-44"`, and is present only when at least one chunk has a numeric `info.chunkIdx`. These `info` values are strings, matching the NvSchema-compatible response.
- Copies its remaining fields from one representative chunk. The `representative` setting selects that chunk.
- Merges the `llm.queries` lists of its chunks, capped at 200 entries. `info.mergedQueryCount` holds the true total and is present only when at least one chunk carried queries.

### What is consolidated

The consolidated view includes only:

- Realtime RT-VLM incident documents. These carry `info.chunkIdx`. Incidents written by the alert verification path do not carry this field and are excluded.
- Chunks whose `info.verdict` is `confirmed`.

Chunks are grouped by `sensorId` and `category`. Within a group, the chunks are ordered by time and a chunk extends the current event when both conditions hold:

- The gap from the previous chunk's `end` to this chunk's `timestamp` is at most `max_inter_alert_gap_seconds`.
- The span from the event's first `timestamp` to this chunk's `end` is at most `max_event_duration_seconds`.

Otherwise the chunk starts a new event. A single confirmed chunk with no neighbour becomes an event with `info.chunkCount` equal to `"1"`.

Use the raw view (`consolidate=false`) for:

- Forensic inspection of individual chunks and their VLM reasoning.
- Rejected or verification-failed chunks.
- Incidents produced by the alert verification path, which have no `info.chunkIdx`.
- On-demand verification results and any other document that does not meet the realtime confirmed-chunk criteria.

### Configuration

Grouping is tuned in the `rtvi_vlm.consolidation` block of the Alerts Microservice configuration file. The block is present in the developer, Smart Cities, Warehouse, and Helm configurations.

| Setting | Default | Valid values | User effect |
| --- | ---: | --- | --- |
| `max_inter_alert_gap_seconds` | `60` | Integer, 1 to 3600 | A later confirmed chunk starts a new event when its gap from the preceding chunk exceeds this value. |
| `max_event_duration_seconds` | `300` | Integer, 1 to 3600, or `null` | Caps the duration of one event. `null` removes this outer cap. |
| `representative` | `latest` | `latest`, `longest_reasoning` | Selects the chunk that supplies the representative incident fields. `latest` is the newest chunk; `longest_reasoning` is the chunk with the longest `info.reasoning`. |

These settings tune grouping only. They do not enable consolidation. Callers must still request `consolidate=true`. Omitting the whole block applies the defaults shown above.

Values outside the valid ranges are not checked at startup. They are rejected the first time `GET /api/v1/realtime/incidents` is called, and from then on every incidents query, raw or consolidated, fails with HTTP 500 while the service itself still reports healthy. Check the values before deploying.

### Limitations

- Consolidation is opt-in and has no current UI integration.
- At most 10,000 of the newest matching raw chunks are scanned for one consolidated query. A truncated result is reported through `truncated: true`.
- Grouping uses `sensorId` and `category` only. Separate rules that watch the same camera for the same category can be combined into one event.
- A consolidated event's identity is derived from its chunks. It is not a persisted event record and cannot be retrieved by ID.
- Raw and consolidated `total` values have different meanings. Compare them only for the same time window.

The read-time consolidation metrics are described in [Realtime incident consolidation metrics](/vss/system-components/analytics-microservices/alerts-microservice#realtime-incident-consolidation-metrics).
