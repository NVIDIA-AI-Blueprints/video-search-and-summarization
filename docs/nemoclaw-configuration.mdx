## Brev hardware and CSP selection

The default [Brev launchable](https://brev.nvidia.com/launchable/deploy/now?launchableID=env-2tYIjRXL4eMCbH9Az8mJC5WPAI4) is available for the notebook path. Before launching the instance, you can also edit the launchable to choose a different hardware profile, such as GPU or CPU shape, and cloud service provider (CSP).

In the Brev launchable editor, select the hardware profile and CSP that match your deployment target and available capacity, then launch the instance. Review [Hardware Requirements](/prerequisites#hardware-requirements) and [Development Profile GPU Requirements](/prerequisites#development-profile-gpu-requirements) before selecting the hardware profile.

After the instance starts, keep the `HARDWARE_PROFILE` value in `deploy_vss_orchestrator.ipynb` aligned with the selected machine. Brev controls the cloud VM shape, while `HARDWARE_PROFILE` controls the VSS deployment assumptions used by the orchestrator.

## Two notebooks

The setup path uses two notebooks that run in order on the VSS host:

* `deploy_nemoclaw.ipynb` configures the agent model provider and installs and onboards the NemoClaw sandbox. Its variables cover:

  * The agent chat model and its credentials.
  * The NemoClaw installer pin and inference proxy.
  * The sandbox name and agent runtime.
  * The dashboard and webhook settings.
  * The host paths the notebook reads.

* `deploy_vss_orchestrator.ipynb` prepares the host, starts the VSS Orchestrator MCP server, and deploys VSS from the Agent UI. Its variables cover:

  * The NVIDIA credentials.
  * The hardware profile.
  * The deployed VSS LLM and VLM endpoints, and the GPU device IDs.
  * The MCP server bind address.
  * The VSS UI and external-IP networking values.

## Agent model versus VSS models

The two notebooks configure two different model surfaces:

* `NEMOCLAW_*` variables in `deploy_nemoclaw.ipynb` configure the agent chat model that operates VSS.
* `LLM_*` and `VLM_*` variables in `deploy_vss_orchestrator.ipynb` configure the LLM/VLM endpoints used by the deployed VSS services when `docker_generate` creates profile artifacts.

## MCP server environment

The orchestrator MCP server reads credentials, hardware profile, remote VSS model endpoints, and device IDs at startup. In `deploy_vss_orchestrator.ipynb`, Section 4 maps the notebook variables into the MCP server environment before launching `uv run nat mcp serve`.

`docker_generate` then merges those values with the selected profile `.env` and any per-call `env_overrides`. For the full resolution order and tool payloads, see [vss-orchestrator-mcp](/vss-orchestrator-mcp).

## VSS Orchestrator MCP config YAML

The MCP server loads `deploy/docker/scripts/vss_orchestrator_mcp_config.yml`. The defaults work for most deployments. Edit this file only when you need different host paths or hardware-specific env overrides, then restart the MCP server (`deploy_vss_orchestrator.ipynb` Section 4) so the changes take effect.

Path settings under `function_groups.vss_orchestrator`:

| Setting | Description |
| --- | --- |
| `mdx_data_dir` | Writable VSS data directory used for generated deployments. Overrides any `VSS_DATA_DIR` value in the selected profile `.env`. Default: `~/video-search-and-summarization/.mdx_data`. |
| `output_dir` | Directory where `docker_generate` stores generated env and compose artifacts. Default: `~/video-search-and-summarization/.orchestrator-artifacts`. |
| `deployments_dir` | Absolute path to `deploy/docker`. |
| `source_compose_yaml` | Absolute path to `deploy/docker/compose.yml`. |
| `source_env` | Absolute path template for profile `.env` files. Supports the `{profile}` placeholder. |

Hardware overrides under `model_resolution.hardware` apply when `HARDWARE_PROFILE` matches. Edge profiles (`DGX-SPARK`, `IGX-THOR`, `AGX-THOR`) also use `edge_device_ids` and `edge_allowed_profiles`. Defaults you may adjust for edge systems:

| Profile | Setting | Default and purpose |
| --- | --- | --- |
| `DGX-SPARK` | `LLM_NAME` / `LLM_NAME_SLUG` | Local Spark NIM FP8 variant when a local LLM is used. |
| `DGX-SPARK` | `RTVI_VLM_IMAGE_TAG` / `PERCEPTION_TAG` | SBSA image tags for the local VLM and perception services. |
| `DGX-SPARK` / `base` | `VLM_NIM_KVCACHE_PERCENT` | `0.2`. Local VLM KV-cache sizing for the `base` profile. |
| `DGX-SPARK` / `alerts` | `RTVI_VLLM_GPU_MEMORY_UTILIZATION` | `0.4`. GPU memory utilization for the local RTVI VLM on `alerts`. |
| `IGX-THOR` / `AGX-THOR` | `VLM_NAME`, `RTVI_VLM_*`, `VLM_MODEL_TYPE` | Local Cosmos3 Nano Reasoner VLM settings for Thor edge systems. |
| `IGX-THOR` / `AGX-THOR` | `RTVI_VLLM_GPU_MEMORY_UTILIZATION` | `0.35`. GPU memory utilization for the local RTVI VLM. |

Leave these values alone unless you are tuning GPU memory, swapping a local model or image tag, or pointing the MCP server at a non-default checkout path.

## Optional notebook cells

### Pin Docker version (deploy_nemoclaw.ipynb Section 2.1)

Pins the tested Docker stack before Section 3 creates the sandbox:

* Docker CE `29.4.3`
* buildx `0.33.0`
* Docker Compose `5.1.3`
* containerd `2.2.3`

Run this before Section 3 creates the sandbox. A Docker downgrade restarts `dockerd` and would disrupt live sandbox containers if it ran later in the notebook. When the installed Docker Engine already falls in the tested range (`28.3.3` through `29.5.0`), the downgrade is skipped and the packages are held at their current versions with `apt-mark hold` so later package operations do not drift the instance.

### Verify sandbox, policy, skills, and webhooks (deploy_nemoclaw.ipynb Section 3.8)

Runs additional checks against the live sandbox after Section 3:

* Sandbox phase, namespace, and id.
* Active policy metadata (status, version, hash).
* Agent webhooks reachability when enabled.
* `openclaw plugins doctor` output.
* The registered `vss_orchestrator` MCP status.
* Installed non-bundled skills from `openclaw skills list --json`.
* Workspace `.md` files uploaded to the sandbox.

### Verify host reachability from the sandbox (deploy_vss_orchestrator.ipynb Section 6)

Run only after VSS is deployed. The probe uses `nemoclaw <sandbox> connect` and validates host port reachability through `host.openshell.internal`. Do not replace this with `docker exec` because that can use a different path and produce misleading results.

The notebook reports one of the following results for each checked port:

* `REACHABLE` - an HTTP service answered. `404` and non-policy `403` responses still count because they prove a service is listening, even if `GET /` is not a valid or authorized route.
* `NOT_REACHABLE` - the port is blocked by policy, no service is listening, DNS failed, the connection failed, or the request timed out. Check the `NOTE` column for the reason.

## Agent webhooks

When `AGENT_HOOKS_ENABLED` is true, `deploy_nemoclaw.ipynb` generates a random `AGENT_HOOKS_TOKEN` and configures agent webhooks at `AGENT_HOOKS_PATH` (Section 3.6). Section 3.8 sends a local authenticated `POST` to `http://127.0.0.1:18789/hooks/agent` to confirm acceptance.

Disable webhooks by setting:

```python
AGENT_HOOKS_ENABLED = False
```

## Artifacts and logs

* MCP server log: `<VSS_REPO_DIR>/.orchestrator-artifacts/vss_orchestrator_mcp.log`.
* Generated env artifacts: `<output_dir>/generated.<docker_compose_id>.dry-run.env`.
* Generated compose artifacts: `<output_dir>/compose.resolved.<docker_compose_id>.dry-run.yml`.
* MCP config: `deploy/docker/scripts/vss_orchestrator_mcp_config.yml`.
* The recorded MCP PID is kept in the notebook's Python state as `VSS_ORCHESTRATOR_MCP_PID` and reused by Section 4 to stop a stale server before relaunching.
