## Overview

The [Search Workflow](/vss/vision-agent/agent-workflows/search) lets you query indexed video archives in
natural language. During ingestion, uploaded clips are embedded through
[RTVI-Embed](/vss/appendix/performance/microservices/rt-embed-performance) (Cosmos-Embed1-448p) and
[RTVI-CV](/vss/appendix/performance/microservices/rt-cv-performance)/Behavior Analytics; during query execution, the Vision
Agent decomposes each request, routes to embed search and attribute search as needed, and
optionally verifies candidates with the critic agent (Cosmos3 Nano Reasoner VLM) before
returning timestamped results.

The tables below benchmark that search performance. Query
latency and throughput measurements use the vad-r1-v2 / benchmark query set (121 natural-language queries
over 17 indexed clips) at concurrent query levels 1, 10, 20, and 50, issued through
`vss search run` with the critic agent verifying every returned hit. Each run reports
client-side end-to-end (E2E) average and P90 latency, successful query throughput (QPS),
and per-stage latency. A separate
section reports video upload latency and chunk counts on both platforms for files ranging from short clips to 2-hour sources. Use these numbers to size GPU choice and
expected query latency under concurrent search load on VSS 3.3.

## E2E Performance

Avg and P90 client-side E2E latency and successful query throughput for the 121-query
vad-r1-v2 / benchmark run under increasing concurrent query load. E2E covers the whole
query: decomposition, retrieval, and critic verification of every returned hit.

<Note>
Throughput is bounded by RTVI-VLM, which serves the critic agent. Each query fans out to
five concurrent verification requests (one per returned hit), so the deployment reaches its
VLM inference ceiling at around 10 concurrent queries. Beyond that, throughput is flat and
additional concurrency only adds queue time — see [Reading these numbers](#reading-these-numbers).
</Note>

### Reading these numbers

Successful QPS is flat from 10 concurrent queries onward (0.454, 0.460, 0.454), because the
deployment is already at its VLM inference ceiling by that point. Latency, by contrast,
scales roughly linearly with concurrency — 4.2s, 21.4s, 40.6s, 90.4s — so concurrency past
the knee buys queue depth, not work.

Critic verification accounts for almost all of it. At every load level the per-call VLM
inference time is within a few percent of total query time, and the retrieval stages
(Elasticsearch, embeddings, VST) stay essentially flat as load rises. Sizing a search
deployment for concurrency therefore means sizing RTVI-VLM: give it a dedicated GPU rather
than sharing one with RTVI-CV, raise `RTVI_VLLM_MAX_NUM_SEQS` and `RTVI_VLM_BATCH_SIZE`
within the available GPU memory, or scale it out. Lowering `num_videos_to_evaluate` reduces
the per-query fan-out at the cost of leaving lower-ranked hits unverified.

## Latency Stage Breakdown

Per-stage average and P90 latency breakdown.

<Note>
**Calls/query** is how many times a stage runs within one query. Stages that run more than
once report a **per-call** duration, not the sum, so the figure is comparable with the
end-to-end row. The critic issues its five verifications concurrently, so its per-call time
is also very close to the wall-clock time the critic phase adds to a query.

Stages that fall below 1 ms at every load level — fusion score combination and VLM media
preparation — are omitted.
</Note>
