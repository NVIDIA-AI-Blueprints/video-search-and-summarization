## Overview

The [Search Workflow](/vss/vision-agent/agent-workflows/search) lets you query indexed video archives in
natural language. During ingestion, uploaded clips are embedded through
[RTVI-Embed](/vss/appendix/performance/microservices/rt-embed-performance) (Cosmos-Embed1-448p) and
[RTVI-CV](/vss/appendix/performance/microservices/rt-cv-performance)/Behavior Analytics; during query execution, the Vision
Agent decomposes each request and routes it to embed search, attribute search, or fusion
search, then optionally verifies candidates with the critic agent (Cosmos3 Nano Reasoner
VLM) before returning timestamped results.

The tables below benchmark that search performance. Query
latency and throughput measurements use the vad-r1-v2 / benchmark query set (121 natural-language queries
over 17 indexed clips) at concurrent query levels 1, 10, 20, and 50, issued through
`vss search run <action>` with the critic agent verifying every returned hit. Each run reports
client-side end-to-end (E2E) average and P90 latency, successful query throughput (QPS),
and per-stage latency. A separate
section reports video upload latency and chunk counts on both platforms for files ranging from short clips to 2-hour sources. Use these numbers to size GPU choice and
expected query latency under concurrent search load on VSS 3.3.

| Concurrent queries | 1, 10, 20, 50 |

<Note>
`vss search run` takes an action — `embed`, `attribute`, `tag`, `fusion` or `object` — so
there is no bare `vss search run "<query>"` form. Each benchmark query ran as a single
invocation carrying the decomposed arguments:

```bash
vss search run fusion \
  --query "forklift near the loading dock" \
  --original-query "Was a forklift operating near the loading dock?" \
  --source-type video_file \
  --top-k 5
```

The CLI does not decompose. The **Query decomposition (LLM)** row in the stage tables is a
separate call made before each invocation, against the reasoning LLM at temperature 0 with
thinking disabled, reusing the prompt the Vision Agent's search tool uses
(`services/agent/packages/vss_agents/src/vss_agents/tools/search.py`). That call chooses the
action and rewrites the query for retrieval; `--original-query` carries the user's untouched
question through so the critic verifies against what was actually asked. To reproduce the
decomposition stage you need that LLM call in front of the CLI — running `vss search run`
alone reproduces every other row but not this one.
</Note>

## E2E Performance

Avg and P90 client-side E2E latency and successful query throughput for the 121-query
vad-r1-v2 / benchmark run under increasing concurrent query load. E2E covers the whole
query: decomposition, retrieval, and critic verification of every returned hit.

<Note>
Throughput is bounded by RTVI-VLM, which serves the critic agent. Each query fans out to
five concurrent verification requests (one per returned hit), so the deployment reaches its
VLM inference ceiling at around 10 concurrent queries. Beyond that, throughput is flat and
additional concurrency only adds queue time — see [Reading these numbers](#reading-these-numbers).
</Note>

### Reading these numbers

Successful QPS is flat from 10 concurrent queries onward (0.961, 0.931, 0.950 on H100),
because the deployment is already at its VLM inference ceiling by that point. Latency, by
contrast, scales roughly linearly with concurrency — 2.5s, 9.8s, 19.8s, 42.0s — so
concurrency past the knee buys queue depth, not work. RTX latency tracks within 4% of these
figures at every level.

Critic verification is the largest single cost, and its share grows with load rather than
staying constant. Per-call VLM inference is 68% of E2E at one concurrent query on H100 and
about 90% at 20 and 50; on RTX it runs from 60% to 83%. RTVI-VLM is therefore the first
thing to size: give it a dedicated GPU rather than sharing one with RTVI-CV, raise
`RTVI_VLLM_MAX_NUM_SEQS` and `RTVI_VLM_BATCH_SIZE` within the available GPU memory, or scale
it out. Lowering `num_videos_to_evaluate` reduces the per-query fan-out at the cost of
leaving lower-ranked hits unverified.

It is not the only thing to size past roughly 20 concurrent queries. Retrieval holds near
its single-query cost through 20 — attribute search goes 0.365s to 0.425s on H100 and 0.508s
to 0.712s on RTX — and then degrades sharply at 50, to 2.219s and 10.950s respectively.
Nearly all of that is the RT-Embed text-embedding call that the attribute and fusion paths
share, which climbs from 1.004s to 2.202s on H100 and from 1.817s to 7.829s on RTX. Embed
search, Elasticsearch query execution and VST clip resolution do stay flat throughout. If
you expect sustained load above about 20 concurrent queries, give RTVI-Embed headroom as
well — sizing RTVI-VLM alone stops being sufficient there, and on RTX the attribute path
becomes the second ceiling.
