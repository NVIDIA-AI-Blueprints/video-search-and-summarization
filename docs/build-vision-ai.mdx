<Warning>
Agent Skills are released as **Early Access** and are not intended for use in production environments.
Agent Skills for VSS were validated using Claude Opus 5.
</Warning>

The `vss-build-vision-ai` Skill is the recommended deployment entry point for
VSS. Use it from a coding agent such as Claude Code or Codex when you want to
deploy a ready-made VSS workflow, deploy a warehouse blueprint, or build a
custom vision stack from the VSS microservices.

For developer-profile and custom builds, the Skill can also set up a host-side
NemoClaw harness after the VSS stack is ready. Warehouse deployments do not
support the NemoClaw harness yet.

Unlike runtime Skills that operate a running deployment, `vss-build-vision-ai`
does the build-time work: it chooses the closest validated profile, resolves the
required services, creates deployment artifacts, validates the Docker Compose
plan, deploys the stack when requested, and returns the URL you use afterward.

<Note>
For the fastest first run, use `vss-build-vision-ai` to deploy the `base`
profile from the [Quickstart](/vss/getting-started/quickstart#deploy-the-base-profile).
</Note>

## When to use it

Use `vss-build-vision-ai` when you want to:

- Deploy a pre-built developer workflow such as `base`, `alerts`, `lvs`
  (Video Summarization), or `search`.
- Deploy a warehouse industry blueprint, including 2D, 3D, MV3DT, and
  auto-calibration variants.
- Build a custom stack from capabilities such as dense captioning, object
  detection and tracking, semantic search, alerting, video summarization, or SOP
  compliance monitoring.
- Rebuild a running deployment with additional vision capabilities in one
  resolved stack.
- Tear down a stack that was created by the Skill.

<Warning>
Deploying a rebuild or extension over a running deployment replaces the same
Compose project after you confirm the teardown plan. The default teardown uses `down -v`, which
removes that project's named volumes, including applicable model caches and
service state. `down -v` does not delete bind-mounted data under the configured
`VSS_DATA_DIR`, but the Skill's separate bind-mounted data cleanup does; that
cleanup requires its own confirmation. Back up required state or ask the Skill
for the cache-preserving teardown before you approve the replacement.
</Warning>

Do not use this Skill for ordinary runtime operations after deployment. Once the
stack is running, use the matching runtime Skill from the
[Agent Skills catalog](/vss/vision-agent/agent-skills#available-skills), or
configure the checkout-local `vss` CLI wrapper for tasks such as uploading
video, asking a question, searching an archive, managing alerts, or generating a
report.

## Deployment paths

`vss-build-vision-ai` supports three entry paths.

| Path | Use it for | What the Skill does |
| --- | --- | --- |
| Pre-built developer workflow | Quickstarts and standard workflows | Selects one validated developer profile: `base`, `alerts`, `lvs` (Video Summarization), or `search`. |
| Pre-built industry blueprint | Warehouse deployments | Selects a warehouse variant and expands its validated service list. |
| Custom build | Capability combinations that do not exactly match a stock profile | Starts from the closest profile and creates the smallest delta needed for the requested capabilities. |

## Supported profiles

### Developer workflows

The table summarizes each stock Compose profile. Build Vision AI resolves the
service graph for the requested capabilities and selected harness, so its final
graph can be smaller. In the default Skill-generated `base` deployment, it
keeps the UI, Redis, VIOS, and RT-VLM and removes the in-stack `vss-agent`,
local LLM, and Phoenix. It retains those services only when the request or
another selected capability requires them.

| Profile | Best for | Stock Compose profile capabilities |
| --- | --- | --- |
| `base` | First run, video Q&A, and report generation on short clips | VSS Agent, UI, VIOS, LLM, and RT-VLM. |
| `alerts` | Real-time alerting and alert verification | Alert Bridge, Video Analytics API, VA-MCP, RT-VLM, and optionally RT-CV with behavior analytics. |
| `lvs` (Video Summarization) | Long video summarization | LVS server, RT-VLM, ELK/Kafka, VIOS, and the UI/agent surfaces for summarization workflows. |
| `search` | Natural-language video search | RT-CV detection and tracking, RT-Embed embeddings, Elasticsearch, Video Analytics API, and search services. |

For `alerts`, the Skill asks which mode you want:

- `2d_vlm` for continuous RT-VLM inspection and real-time alert APIs.
- `2d_cv` for RT-CV detections, behavior analytics, and VLM verification.

### Warehouse blueprint

The warehouse path deploys validated industry-profile combinations rather than
composing a custom delta. The Skill asks for the warehouse mode, deployment
variant, size when applicable, and sample dataset.

| Mode | Use it for |
| --- | --- |
| `2d` | Multi-camera RT-DETR perception and warehouse behavior analytics. |
| `3d` | Depth-aware Sparse4D perception with behavior analytics. |
| `mv3dt` | Multi-view 3D tracking with BEV fusion. |
| `auto-calibration` | Producing calibration for a selected warehouse dataset. |

Warehouse deployments register their own sample sources through the warehouse
configurator. Do not manually provision sources during the build path unless you
are working with a separate custom or headless deployment.

## Host preflight and intake

The host must satisfy [Prerequisites](/vss/getting-started/prerequisites) (Linux, GPU, Docker, NVIDIA Container Toolkit, NGC). The Skill's own checks in `skills/vss-build-vision-ai/references/prerequisites.md` also require:

- A Python runner for mandatory service-graph checks and helper scripts. `uv`
  is preferred; Python 3 with PyYAML is also supported. Install `uv` with
  `curl -LsSf https://astral.sh/uv/install.sh | sh`, or install the fallback
  with `python3 -m pip install PyYAML`.
- `curl`, `docker`, and NGC CLI access.

The Skill asks which developer workflow or warehouse variant you want, LLM/VLM locality (local vs remote), and hardware. Defaults follow the selected profile (for example alerts `2d_vlm` vs `2d_cv`). Each answer changes the composed stack (services, `MODE`, GPU placement).

The credential gate is determined by those answers:

| Choice | Credential |
| --- | --- |
| Any standard VSS deployment | `NGC_CLI_API_KEY`; authenticate Docker to `nvcr.io` separately before running the Skill. |
| Default NemoClaw remote endpoint, or another public OpenAI-compatible harness endpoint | `COMPATIBLE_API_KEY` (no default value). Create a key for the default endpoint at [NVIDIA Inference Hub key management](https://inference.nvidia.com/key-management?action=new-key). |
| `build.nvidia.com` model endpoint | `NVIDIA_API_KEY`. |
| Gated or rate-limited Hugging Face model download | `HF_TOKEN`. |
| Self-hosted harness endpoint or no harness | No harness key. Stack-level NGC/model credentials still apply. |

The Skill blocks before deploying when a required key is missing. It does not
silently change the provider or disable the harness.

During host preflight the Skill runs
`deploy/docker/scripts/pin_docker_version.sh` with approval when needed. The
script enforces the supported Docker range and `cgroupfs` setting and can restart
Docker. Run it before starting containers, not on a host where unrelated running
containers may be interrupted without review.

## Custom capability builds

For custom builds, describe the capabilities you want instead of choosing a
profile directly. The Skill owns the capability mapping: it selects the closest
Foundation profile and creates a build-local delta for the services the request
adds or removes.

The Skill includes VIOS as the video input and storage layer for guided custom
builds. It retains ingress only when the requested capability or harness needs a
single public origin, and adds ELK/Kafka only for capabilities that publish to
Kafka or index into Elasticsearch.

### SOP compliance monitoring

SOP compliance monitoring is a custom capability build, not a stock developer
profile. The Skill composes the DS-SOP perception service with Kafka and
Elasticsearch storage, VIOS for live sources, and the SOP reporting tools on
VA-MCP. DS-SOP occupies the perception slot, so the resolved build uses it in
place of RT-VLM.

Ask the Skill to build and deploy the complete capability:

```text title="SOP compliance deployment prompt"
Use the vss-build-vision-ai skill to build and deploy an SOP compliance
monitoring stack. Show the resolved services, GPU placement, source wiring, and
teardown impact before deploying.
```

After the build is ready and a source is producing SOP results, use
`vss-generate-video-report` Mode C with a sensor and time range:

```text title="SOP compliance report prompt"
Generate an SOP compliance report for <sensor> from <start-time> to <end-time>.
```

Mode C is read-only. It verifies that VA-MCP exposes
`video_analytics__get_sop_report`, reads the indexed SOP results for the
requested range, and renders the SOP compliance report. See the
[Agent Skills catalog](/vss/vision-agent/agent-skills#operations) for the
report Skill and its other modes.

### Combine real-time alerting and video summarization

Request the capabilities as one custom build; do not bring up the stock alerts
and LVS profiles separately:

```text title="Combined deployment prompt"
Use the vss-build-vision-ai skill to build and deploy one VSS stack that combines
real-time VLM alerting (2d_vlm) with long-video summarization. Show the resolved
services, GPU placement, and teardown impact before deploying.
```

The build records exactly one stock profile as `FOUNDATION` in
`_builds/<name>/override.env`, but correctness is determined by the resolved
service graph rather than by forcing either stock profile to run unchanged.
`MODE=2d_vlm` applies to the alerting path; the Skill must recompute every
Foundation-derived configuration path and value in the build-local override
instead of applying the LVS profile's derived paths to that mode.

The resolved stack contains one `alert-bridge`, one `lvs-server`, one LLM, and
shared instances of RT-VLM, VIOS, Kafka, Redis, Elasticsearch, Logstash,
ingress, and `vss-video-analytics-api`, plus any selected agent or harness. It
must set the alerts mode to `2d_vlm`, enable
always-on alerting and RT-VLM Kafka output, and retain the LVS server and its
Kafka summary path. The Skill writes the exact `COMPOSE_PROFILES` and dependent
environment values to `_builds/<name>/override.env`; do not assemble that list
by concatenating the two stock profile files.

Before bring-up, the Skill validates `_builds/<name>/resolved.yml`. After
readiness, `vss configure check` must report `summarize` as available, and the
Alert Bridge, RT-VLM, LVS, and Video Analytics API services must be running.
Harness-free builds use the `vss-manage-alerts` Skill for alert rules and
incident queries; it calls Alert Bridge directly and does not require the
in-stack VSS Agent.

This combination uses one LLM for `lvs-server` and one shared RT-VLM; it adds no
second model process of either type. Use the real-time alerts GPU row as the
starting model-placement cost: on H100 or RTX PRO 6000 Blackwell, plan for two
GPUs in the shared layout or three with dedicated model placement.
LVS work and continuous alert inference contend for the same RT-VLM, so the
Skill must still validate measured memory headroom and stream/request capacity
on the target host. A stock sizing row is not a throughput guarantee for the
combined workload.

<Warning>
Developer profiles default to the same Compose project name, `vss`, and also use
singleton container names and host ports. Running stock alerts and LVS commands
side by side on one host is not supported; changing only
`COMPOSE_PROJECT_NAME` does not remove those collisions. A custom combined build
follows the replacement and teardown behavior described under
[When to use it](#when-to-use-it), so review the teardown plan before
proceeding.
</Warning>

## Agent harness

When a developer-profile or custom build includes the in-stack VSS Agent, the
Skill asks whether to deploy a host-side agent harness. The default harness is
NemoClaw, which runs outside the Docker Compose project and operates the
deployed stack through its public ingress URL.

If you choose no harness, operate the deployment from the host with the `vss`
CLI. If you explicitly request the in-stack VSS Agent, the Skill preserves that
agent instead.

<Note>
A harness is not a Docker Compose service. The Skill never adds `nemoclaw` to
`COMPOSE_PROFILES`; it installs and starts the harness only after the VSS stack
passes readiness checks.
</Note>

Warehouse deployments do not enter the NemoClaw harness flow. The Skill deploys
the selected Warehouse variant as-is; for the 2D `bp_wh` variant, that means
preserving the in-stack VSS Agent.

## What the Skill creates

For each build, `vss-build-vision-ai` writes build-local artifacts under
`_builds/<name>/`:

```text
_builds/<name>/
|-- override.env
|-- compose.yml
|-- patches/      # optional; changed or new services only
`-- resolved.yml
```

Warehouse builds also generate `configurator.env` because the warehouse
configurator reads its own environment file.

The Skill validates `resolved.yml` before deployment. If deployment is requested,
it starts exactly the validated Compose plan and waits for profile-specific
readiness checks before returning.

## After deployment

After the Skill returns the deployment URL, configure the checkout-local `vss`
CLI against that origin. Run this from the VSS Blueprint checkout:

```bash
VSS_REPO_ROOT="${VSS_REPO_ROOT:-$PWD}"
vss() { uv run --project "${VSS_REPO_ROOT}/libs/vss" vss "$@"; }
vss --version

vss configure --base-url "<VSS_PUBLIC_URL>"
vss configure check
```

Then use the runtime Skills or CLI command groups that match the deployed
services:

- `vss-manage-video-io-storage` or `vss vios` for sensors, uploads, clips, and
  snapshots.
- `vss-ask-video` or `vss vlm` for one-off visual questions.
- `vss-generate-video-report` for report generation.
- `vss-summarize-video` or `vss summarize` for video summaries.
- `vss-search-archive` or `vss search` for archive search.
- `vss-manage-alerts` and `vss-query-analytics` for alerts and analytics data.
