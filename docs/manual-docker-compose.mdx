Use this guide to manage the stock Compose deployment from a host terminal.
Complete the shared [prerequisites](/vss/getting-started/prerequisites),
[download steps](/vss/getting-started/quickstart#download-sample-data-and-deployment-package),
and registry login first. For the recommended agent-assisted route, use the
[Quickstart](/vss/getting-started/quickstart).

### Docker Compose deployment

Use the selected developer profile with its checked-in `.env` file and a local
`user-overrides.env` file throughout the native Docker Compose procedure below.

<Note>
- Set the NGC CLI API key, then run the deploy commands for your GPU type. Set `HF_TOKEN` only when the selected model downloads gated or rate-limited weights from Hugging Face. See [NGC + Hugging Face API Keys](/vss/getting-started/prerequisites#ngc--hugging-face-api-keys).
- Refer to [Configure the LLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-llm) and [Configure the VLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm) for all LLM and VLM (local and remote) configuration options.
- For **Nemotron Omni** video+audio with a remote VLM, set `ENABLE_AUDIO=true` and follow [Using Nemotron Omni (audio-enabled remote VLM)](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm#using-nemotron-omni-audio-enabled-vlm) in [Configure the VLM](/vss/vision-agent/vss-agents/agent-customization/customize-models/configure-the-vlm).
- For advanced settings and Agent Customization, edit the profile `user-overrides.env`.
</Note>

```bash title="Run in the host terminal"
# Set the NGC CLI API key. Set HF_TOKEN only when the selected model requires it.
export NGC_CLI_API_KEY='<your-ngc-api-key>'
# export HF_TOKEN='<hf-token>'

# Authenticate Docker to pull VSS release images, NIM, and other NGC images.
printf '%s' "$NGC_CLI_API_KEY" | \
  docker login nvcr.io --username '$oauthtoken' --password-stdin

```

See [Configuration](/vss/system-components/configuration) for common variables,
valid values, defaults, and env-file precedence. The complete profile-specific
template is
`deploy/docker/developer-profiles/dev-profile-base/overrides.env`.

Select a hardware tab, then a deployment mode. **Shared GPU** runs the local
LLM and integrated RT-VLM on the same GPU. **Dedicated GPU** assigns them to
separate GPUs with `LLM_DEVICE_ID` and `RT_VLM_DEVICE_ID`. Keep
`VLM_DEVICE_ID` aligned with `RT_VLM_DEVICE_ID` for local integrated RT-VLM:
the local VLM service binds the GPU named by `VLM_DEVICE_ID`, while the RT-VLM
container binds the GPU named by `RT_VLM_DEVICE_ID`.

From the repository checkout root, enter the Compose deployment directory:

```bash title="Run in the host terminal"
cd deploy/docker
```

`overrides.env` is the checked-in template. Copy it to any
filename matching `*-overrides.env` before selecting a layout. Files matching
that pattern are ignored by Git so local settings and credentials are not
committed. The commands below use `user-overrides.env` as a concrete example;
if you choose another name, use it consistently in every `--env-file` argument.
Repeat the copy only when you want to discard prior layout changes:

```bash title="Run in the host terminal"
PROFILE=base
cp "developer-profiles/dev-profile-${PROFILE}/overrides.env" \
  "developer-profiles/dev-profile-${PROFILE}/user-overrides.env"
```

Before starting Compose, complete the host settings and select one hardware
layout below in `deploy/docker/developer-profiles/dev-profile-base/user-overrides.env`.

**Environment-variable overrides:** In `deploy/docker/developer-profiles/dev-profile-base/user-overrides.env`, update existing values in place; add a variable only when it is absent. `COMPOSE_PROFILES` is derived from values above it, so appending duplicate model-mode or model-slug variables can select the wrong services.

On GB300, DGX Spark, and other SBSA hosts, export
`VSS_CONTAINER_TAG_SUFFIX=-sbsa` in the shell before running Compose. This
appends `-sbsa` to the managed RT-CV, RT-Embed, RT-VLM, and Video Summarization
image tags while preserving the shared `VSS_CONTAINER_TAG` release channel. Do
not put the suffix in `user-overrides.env`: `containers.env` derives the image
tags before later env files are read.

**Host-path and service-address overrides (all hardware profiles):**

- `VSS_APPS_DIR`: Absolute path to this repository's `deploy/docker` directory.
- `VSS_DATA_DIR`: Absolute writable host directory for downloaded models, videos, and service data.
- `HOST_IP`: IP address or hostname that clients use to reach services on this VSS host. Set it to an address reachable by the intended clients.
- `EXTERNAL_IP`: Address VSS puts in externally reachable service URLs. It defaults to `${HOST_IP}`; on a cloud host or when clients connect from outside the host network, set it to the instance's public address or external hostname.


Set these required placeholder values in the existing assignments:

```ini
VSS_APPS_DIR=/absolute/path/to/video-search-and-summarization/deploy/docker
VSS_DATA_DIR=/absolute/path/to/vss-apps-data
HOST_IP=<reachable-host-ip-or-name>
```

**Prepare host data directories before starting Compose.** Export
`VSS_DATA_DIR` with the same absolute path you set in `user-overrides.env`, then
run this block. The guard stops before `mkdir` or `chmod` if the value is absent
or is not absolute:

```bash title="Run in the host terminal"
: "${VSS_DATA_DIR:?Export VSS_DATA_DIR with the value from user-overrides.env}"
case "$VSS_DATA_DIR" in
  /*) ;;
  *) echo "VSS_DATA_DIR must be an absolute path" >&2; exit 1 ;;
esac
mkdir -p \
  "$VSS_DATA_DIR/data_log/analytics_cache" \
  "$VSS_DATA_DIR/data_log/calibration_toolkit" \
  "$VSS_DATA_DIR/data_log/elastic/data" \
  "$VSS_DATA_DIR/data_log/elastic/logs" \
  "$VSS_DATA_DIR/data_log/kafka" \
  "$VSS_DATA_DIR/data_log/nvstreamer/vst_data" \
  "$VSS_DATA_DIR/data_log/redis/data" \
  "$VSS_DATA_DIR/data_log/redis/log" \
  "$VSS_DATA_DIR/data_log/vss_video_analytics_api" \
  "$VSS_DATA_DIR/data_log/vst/clip_storage" \
  "$VSS_DATA_DIR/agent_eval/dataset" \
  "$VSS_DATA_DIR/agent_eval/results" \
  "$VSS_DATA_DIR/models"
chmod -R a+rwx \
  "$VSS_DATA_DIR/data_log" \
  "$VSS_DATA_DIR/agent_eval" \
  "$VSS_DATA_DIR/models"
```

<Warning>
These broad write permissions are intended for development deployments whose
containers use multiple user IDs. For production, restrict host directory
ownership and permissions to the identities used by your deployment. See
[Secure Deployment](/vss/appendix/additional-deployments/secure-deployment#host-filesystem-permissions).
</Warning>

**Default container image tag**

`containers.env` uses `VSS_CONTAINER_TAG` as the default tag for all images.
Export the tag selected for this documentation branch before choosing a hardware
layout:

```bash title="Run in the host terminal"
export VSS_CONTAINER_TAG="${VSS_DOCS_IMAGE_TAG:-develop-latest}"
```

Any service-specific image tag or tag suffix shown inside a hardware tab
supersedes or augments this common default. Use the SBSA settings shown in the
GB300 and DGX Spark tabs when deploying on those platforms.

<Note>
For DGX Spark, IGX Thor, and AGX Thor, the tabs below show the remote-LLM
layout recommended for latency. The checked-in base configuration also supports a co-located local LLM and
RT-VLM, but those local layouts have not
yet been measured on the target hardware. See
[Edge Deployment](/vss/appendix/additional-deployments/edge-deployment) for
their settings and validation caveat.
</Note>

### Shared GPU memory and port checks

The base template reserves `RTVI_VLLM_GPU_MEMORY_UTILIZATION=0.4`, leaving
headroom for the local LLM and CUDA allocations on the reviewed 96 GB GPU.
Inspect `nvidia-smi` before launch and compare the selected layout with the
[GPU requirements](/vss/getting-started/prerequisites#development-profile-gpu-requirements).
A different model, GPU, or active workload requires a fresh memory budget.

Before launch, inspect `df -h` for the model/data filesystem and `ss -ltn`
for occupied ports. If Redis reports `address already in use` on port 6379,
change the existing `REDIS_HOST_PORT=6379` assignment to `REDIS_HOST_PORT=6380`
in `user-overrides.env`, choose another free port if needed, and rerun the same
Compose command. Container traffic still uses Redis's internal port 6379.

`--wait --wait-timeout 1200` makes a failed health check fail the launch command.
On timeout, inspect `docker compose ... ps --all` and the failing service's
logs before retrying. Container creation alone does not establish readiness.

After replacing every placeholder in the selected layout, from `deploy/docker`
validate the resolved configuration, then start the profile:

```bash title="Run in the host terminal"
PROFILE=base
docker compose -f compose.yml \
  --env-file containers.env \
  --env-file "developer-profiles/dev-profile-${PROFILE}/.env" \
  --env-file "developer-profiles/dev-profile-${PROFILE}/user-overrides.env" \
  config --quiet

docker compose -f compose.yml \
  --env-file containers.env \
  --env-file "developer-profiles/dev-profile-${PROFILE}/.env" \
  --env-file "developer-profiles/dev-profile-${PROFILE}/user-overrides.env" \
  up --detach --pull always --force-recreate --build --wait --wait-timeout 1200
```

Review every unset-variable warning from `config --quiet` against the selected
profile before running `up --detach --pull always --force-recreate --build`. A zero exit code confirms that Compose could
render the model; it does not prove that every operationally required value is
set. Variables used only by inactive profiles can also produce warnings.

Docker Compose downloads the required containers from the configured NGC registries and starts the agent. Depending on
your network speed, this may take a few minutes.

<Note>
When using a remote VLM of model-type `nim` (not `openai`), see [How does a remote `nim` VLM access videos?](/vss/appendix/faq#how-does-a-remote-nim-vlm-access-videos) for access requirements.
</Note>

<Note>
**Switch Agent Workflows:** Use the matching `developer-profiles/dev-profile-<profile>/.env` plus `user-overrides.env`. Later `--env-file` values win.

Switch profiles by changing the `dev-profile-<profile>` directory, not by setting `MODE` to `base`/`lvs`/`search`/`alerts`. Those names are profile directories. For the **alerts** profile only, `MODE` is:

- [Alert Verification Workflow](/vss/vision-agent/agent-workflows/alert-verification#direct-docker-compose-overrides) — `MODE=2d_cv`
- [Real-Time Alert Workflow](/vss/vision-agent/agent-workflows/real-time-alerts#direct-docker-compose-overrides) — `MODE=2d_vlm`

For a manual alerts deployment, setting `MODE` alone is not sufficient. Follow
the linked workflow and copy its complete common override block into
`dev-profile-alerts/user-overrides.env`; that block selects the matching
service set, message-bus behavior, and agent/UI settings together.

</Note>

### Verify the manual in-stack Agent deployment

Once the deployment is complete, check that all the containers are running and healthy:

```bash title="Run in the host terminal"
docker ps
```

Once all the containers are running, you can access the agent UI at `http://<HOST_IP>:7777/`.

#### If the UI Doesn't Load

If `http://<HOST_IP>:7777/` does not open, run these checks before redeploying:

1. Check the VSS Agent health endpoint:

   ```bash title="Run in the host terminal"
   curl -fsS "http://<HOST_IP>:8000/health"
   ```

2. Confirm the expected base-profile containers are running and healthy:

   ```bash title="Run in the host terminal"
   docker ps --format "table {{.Names}}\t{{.Status}}\t{{.Ports}}"
   ```

   Look for the VSS Agent, VSS Agent UI, VIOS/VST, Nemotron LLM,
   `vss-rtvi-vlm`, and Phoenix containers.

3. If containers are unhealthy or certain services are unresponsive, check the corresponding
   container logs for startup, or configuration errors.

4. If containers are healthy but the UI or workflow is still unavailable, check
   whether the host firewall is blocking container-to-host traffic. See
   [Bridge-network container cannot reach a VSS service on the host](/vss/appendix/faq#bridge-network-container-cannot-reach-a-vss-service-on-the-host).

For the recommended agent-guided deployment path, see
[Deploy the base profile](/vss/getting-started/quickstart#deploy-the-base-profile).

<Note>
The agent generates both Markdown (`.md`) and PDF (`.pdf`) reports. Generated reports are accessible at

### Teardown the Agent

To teardown the agent, run the following command:

```bash title="Run in the host terminal"
cd deploy/docker
PROFILE=base
docker compose -f compose.yml \
  --env-file containers.env \
  --env-file "developer-profiles/dev-profile-${PROFILE}/.env" \
  --env-file "developer-profiles/dev-profile-${PROFILE}/user-overrides.env" \
  down -v --remove-orphans
```

This command stops the manually deployed base-profile containers and removes
their Compose volumes.
