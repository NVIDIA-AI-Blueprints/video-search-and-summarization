## Overview

The **VSS Configurator** manages hardware profile settings and sensor configuration for the Warehouse Operations Blueprint. The Profile Configuration Manager applies deployment-time file changes for the `2d`, `3d`, and `mv3dt` modes. The Sensor Configuration Manager then discovers sensors, processes calibration when enabled, publishes configuration events, and registers cameras with VST.

For the service's configuration reference and API details, see [VSS Configurator](/vss/system-components/configuration/vss-configurator). This page describes how the service is used in the warehouse blueprint.

## System Flow

| Step | Stage | Result |
| --- | --- | --- |
| 1 | Start | `entrypoint.main` reads feature flags and launches profile configuration when enabled. |
| 2 | Select and validate | `ProfileConfigManager` selects `MODE` and `HARDWARE_PROFILE`, validates environment values, and loads the ordered plan from `blueprint_config.yml`. |
| 3 | Compute | Derived values include the hardware ceiling and `final_stream_count = min(NUM_STREAMS, effective maximum)`. |
| 4 | Mutate files | The manager applies YAML, JSON, key=value, and text replacement operations and, when enabled, recomputes BEV groups for mounted `3d` or `mv3dt` calibration; enabled operations normally create backups. |
| 5 | Mark ready | Successful profile work creates `PROFILE_CONFIG_READY_FILE`. This signals profile completion only. |
| 6 | Discover sensors | Gunicorn starts the background sensor phase. It polls NVStreamer, validates main streams, and builds an in-memory sensor map. |
| 7 | Integrate | The sensor phase optionally reads or updates calibration, publishes configuration to SDR, and registers accepted RTSP cameras with VST. |

### File Operation Types

The profile manager dispatches `yaml_update`, `json_update`, `text_config_update`, `text_replace`, `file_management`, and `recompute_bev_groups` operations in blueprint order. Warehouse `keep_count` is currently disabled.

## Runtime Inputs

These inputs are used by the sensor phase after profile completion. Calibration paths, `CALIBRATION_MODE`, and sensor-source inputs may also be used by profile-time BEV recomputation as listed above. Most sensor-phase inputs change runtime state or mounted data, not repository configuration files.

| Variable Group | Runtime Function | Affected State or File |
| --- | --- | --- |
| `ENABLE_SENSOR_CONFIGURATOR` | Start or skip the sensor API process | Process state |
| `SENSOR_INFO_SOURCE`; `SENSOR_FILE_PATH` | Choose `nvstreamer`, `msb`, file, or `not_required` | Source API or `${SENSOR_FILE_PATH}` |
| `NUM_STREAMS` | Readiness threshold for NVStreamer list; zero uses stable-count behavior | No file |

## Discussion Points and Confirmed Behavior

### NUM_STREAMS Contract

- At profile time, `final_stream_count` is the requested count capped by the selected hardware limit. It sizes DeepStream and writes NVStreamer `data.nv_streamer_sync_file_count`.
- At runtime, the sensor manager reads the original `NUM_STREAMS` again. A non-empty NVStreamer list is considered complete when `count >= NUM_STREAMS`.
- The `>=` test is only a readiness gate. If `NUM_STREAMS` is 4 and NVStreamer returns 6, the configurator does not take the first four; all six returned groups continue through main-stream and health validation.
- The specific video files and their ordering are selected by NVStreamer, not by calibration order. Calibration enriches matching sensor IDs; it does not choose the first N cameras.
- If the hardware cap is lower than `NUM_STREAMS`, profile files may be sized for the cap while runtime waits for the original request. A partial non-empty list can proceed after `NVSTREAMER_STREAMS_ENDPOINT_TIMEOUT`.

### Calibration Freshness

With `ENABLE_CALIBRATION_PROCESS=true`, the sensor phase obtains calibration by fetch, upload, or mount and uses matching sensor IDs to add group and region metadata. In warehouse `3d`, the configurator, VST, DeepStream, Behavior Analytics, and the import container mount the same host calibration file at different container paths. A write becomes visible through those mounts, but an already-running service is not forced to reload it.

In the warehouse `3d` and `mv3dt` profiles, `RECOMPUTE_BEV_CENTERS_ENABLED=true` enables the profile-time `recompute_bev_groups` operation. With `CALIBRATION_MODE=mount`, it validates the configured camera set, recomputes BEV groups, and updates the mounted calibration file before `PROFILE_CONFIG_READY_FILE` is written. This operation runs before Gunicorn starts the background sensor phase.

Both calibration import containers depend on their configurator becoming healthy through `/readyz`, which checks profile readiness when profile configuration is enabled. The import scripts also wait for the Video Analytics API before uploading the mounted calibration. Enabled profile-time BEV recomputation therefore finishes before these imports start. Sensor discovery, calibration mapping, VST registration, and SDR publication still run separately in the background sensor phase. Later calibration edits may require a consumer reload or re-import; the startup gate does not trigger those actions automatically.

### SDR Publication

When `SEND_CONFIG_TO_SDR=true`, the configurator publishes one configuration event for each sensor that survived NVStreamer main-stream and health checks. `MESSAGE_BROKER_TYPE` selects Redis or Kafka; `WDM_REDIS_*` or `WDM_KFK_*` supplies the destination and key fields. The event carries camera ID, RTSP URL, region and group when available, and downstream topic metadata. This is separate from the VST camera-add HTTP request. Publish errors are logged and do not make profile readiness fail. Warehouse `2d` sets this flag to false; `3d` and `mv3dt` set it to true.

### Profile Readiness and VST Startup

The profile readiness marker is a Compose startup gate for dependent services. It means the enabled profile file operations completed successfully, including profile-time BEV recomputation in `3d` and `mv3dt` when enabled. It does not mean sensors were discovered, runtime calibration mapping finished, cameras were added to VST, or SDR received messages. Those actions run later in the background sensor thread.

## Decisions and Actions

The Current Behavior column records the implementation behavior. Use the Decision to Record and Suggested Owner columns to guide a configuration review.

| Topic | Current Behavior | Decision to Record | Suggested Owner |
| --- | --- | --- | --- |
| Stream count | Profile files use capped `final_stream_count`; runtime discovery reads original `NUM_STREAMS`. | Use one canonical count or define mismatch behavior. | Configurator and deployment |
| Extra streams | `count >= NUM_STREAMS` ends the wait; the returned list is not truncated. | Accept all, cap deterministically, or reject the mismatch. | NVStreamer and configurator |
| Calibration | Enabled profile-time BEV recomputation completes before profile readiness and calibration imports; later edits do not force running consumers to reload. | Define consumer reload and re-import behavior for later calibration edits. | VST DeepStream and analytics |
| Readiness | `PROFILE_CONFIG_READY_FILE` covers profile mutation only. | Keep profile-only readiness or add a separate sensor-ready signal. | Configurator and deployment |
| SDR errors | Publication is separate from VST registration; errors are logged without failing readiness. | Define retry, metric, alert, and escalation policy. | SDR and configurator |
| Worker count | Each Gunicorn worker starts its own sensor-processing thread. | Enforce one worker or add leader election and idempotency. | Configurator |
