This guide provides a comprehensive step-by-step walkthrough to help you quickly set up and start using the Warehouse Blueprint.

The Warehouse Blueprint is a video analytics solution that supports real-time object detection, tracking, and analytics. It offers two message broker options to accommodate different deployment scenarios:

- **Kafka**: High-throughput message broker optimized for datacenter deployments with robust persistence and scalability.
- **Redis Streams**: Lightweight message broker ideal for edge deployments with minimal memory footprint and low-latency requirements.

Choose the message broker based on your deployment environment: Kafka for centralized datacenter installations, or Redis for distributed edge locations where resources are constrained.

## Components Overview

The high-level diagram illustrates the components of the Warehouse Blueprint. The diagram features the 2D, 3D, or MV3DT blueprint. The Agent communicates with the Blueprint's data services through APIs.

The following diagram shows the major components of the Warehouse Blueprint:

![Major components of Warehouse Blueprint](/assets/images/major_components_of_warehouse_blueprint.png)

Camera streams are ingested by VST/VMS, processed by RT-CV (perception) and Behavior Analytics microservices, with CV metadata and alerts published to the Message Bus and persisted via Storage Services.

The following diagram shows how AI Agents interact with the Warehouse Blueprint:

![Agent interaction with Warehouse Blueprint](/assets/images/agent_interaction_with_warehouse_blueprint.png)

The Agent orchestrates MCP servers for Video IO, Video Analytics, and Report Generation, leveraging Nemotron (LLM) and Cosmos-Reason (RTVI-VLM) inference microservices.

## Prerequisites

Before you begin, ensure all of the prerequisites are met. See [Prerequisites](/vss/vision-agent/agent-workflows/industry-specific-examples/warehouse-operations-blueprint/prerequisites) for more details.

## Deployment Options

The Warehouse Blueprint offers flexible deployment options with the following profiles:

| Profile Type | Features | Constraints |
| --- | --- | --- |
| 2D Vision AI Profile | 2D single-camera detection, tracking, and analytics | Model trained on real-world data |
| 2D Vision AI with Agents Profile | 2D single-camera detection, tracking, analytics, and VSS agent integration | Model trained on real and synthetic data |
| 3D Vision AI Profile | 3D multi-camera detection, tracking, and analytics | Model trained on synthetic data, recommended for simulated environments |
| MV3DT Vision AI Profile | 3D multi-camera detection, tracking, and analytics using RT-DETR + MV3DT | RT-DETR model trained on real-world data, MV3DT distributed 3D tracking via camera projection matrices |

## Download Warehouse Artifacts

This section guides you through the steps to download the Warehouse Blueprint artifacts.

### Setup NGC Access

```bash
# Setup NGC access
export NGC_CLI_API_KEY=<NGC_CLI_API_KEY>
export NGC_CLI_ORG='nvidia'
```

#### Download the Deployment Package

Perform this on the machine where you intend to deploy the blueprint.

<Note>
**Git LFS required:** The repository uses Git LFS for large files. Install it before cloning or pulling. For example, on Ubuntu/Debian: `sudo apt-get install git-lfs`. On other systems, see [Git LFS installation](https://git-lfs.com/).
</Note>

```bash
git clone https://github.com/NVIDIA-AI-Blueprints/video-search-and-summarization.git
cd video-search-and-summarization
git checkout tags/v3.2.1
git lfs install
git lfs pull
cd deploy/docker
# This is the path to the deploy/docker directory. Set VSS_APPS_DIR in industry-profiles/warehouse-operations/overrides.env.
#VSS_APPS_DIR="/path/to/deploy/docker"
```

### Warehouse App Data

Warehouse App Data contains sample video datasets, pre-trained TensorRT models (RT-DETR for 2D and MV3DT, Sparse4D for 3D, NvDCF tracker, BodyPose3DNet for MV3DT), camera calibration data, and configuration templates for deploying 2D, 3D, and MV3DT warehouse profiles.

The package includes the following MP4 datasets at 1920x1080 and 30 FPS:

Every included dataset is supported by every Warehouse profile.

| Dataset | Cameras | Duration | Scene Details |
| --- | --- | --- | --- |
| `nv-warehouse-4cams` | 4 | Approximately 10 minutes per camera (600 seconds) | Real-world high-angle aisle footage with racks, palletized inventory, workers in safety vests, boxes, shrink-wrapped pallets, forklift activity, and pallet movement. |
| `warehouse-loading-dock-3cams-synthetic` | 3 | 4 minutes per camera (240 seconds) | Synthetic loading dock footage with overhead views, loading bays, yellow-and-black floor safety zones, boxes on pallets, and forklift equipment. |
| `warehouse-4cams-20mx20m-synthetic` | 4 | 5 minutes per camera (300 seconds) | Synthetic 20mx20m 3D warehouse scene with overlapping corner-mounted camera views, numbered zones, palletized boxes, forklifts, workers, safety boundaries, and barriers. Used for multi-camera tracking, spatial analytics, and cross-camera object re-identification. |
| `warehouse-loading-dock-3cams-synthetic-degraded` | 3 | 4 minutes per camera (240 seconds) | Degraded synthetic loading dock footage with low-light and lower-quality camera visuals, representing deployments where camera feeds vary in quality. Used for testing detection, tracking, and analytics under degraded visibility. |

<Note>
After extracting the package, set `VSS_DATA_DIR` in `industry-profiles/warehouse-operations/overrides.env` to point to the extracted data directory.

If you use your own videos or RTSP streams, they must have a resolution of `1920 x 1080` and be encoded without B-frames.

To check for and remove B-frames, see [the FAQ guidance](/vss/vision-agent/agent-workflows/industry-specific-examples/warehouse-operations-blueprint/operations-monitoring-troubleshooting-faq-known-limitations/faq#my-videos-produce-incorrect-timestamps-for-messages-or-are-processed-over-an-extended-duration).

For custom video inputs, provide time-synchronized MP4 videos encoded without B-frames that are at least 60 seconds long and all videos should have the same duration.

AMC relies heavily on moving people in the input videos. Ensure that the videos contain a sufficient number of clearly visible moving people.
</Note>

```bash
ngc registry resource download-version "nvstaging/vss-warehouse/vss-warehouse-app-data:v3.3.0-09042026"

# OR Manually download the tar file from NGC
# URL https://catalog.ngc.nvidia.com/orgs/nvstaging/teams/vss-warehouse/resources/vss-warehouse-app-data?version=v3.3.0-09042026

# Extract the package

cd vss-warehouse-app-data_vv3.3.0-09042026
tar -xvf vss-warehouse-app-data.tar.gz

# Set permissions

sudo chmod -R 777 /path/to/vss-warehouse-app-data

# This is the path to the extracted data directory. Set VSS_DATA_DIR in industry-profiles/warehouse-operations/overrides.env.
#VSS_DATA_DIR="/path/to/vss-warehouse-app-data"
```

<Note>
**Extended and minimal deployments**

Minimal deployments are available for the Kafka and Redis 2D, 3D, and MV3DT profiles and are recommended on resource-constrained edge systems. They exclude ELK (Elasticsearch, Logstash, and Kibana), Video Analytics API, HAProxy, monitoring, and import helpers.

In the VST UI, metadata for live streams is read from Kafka or Redis, while metadata for recorded streams is read from Elasticsearch. Because Elasticsearch is not deployed in a minimal configuration, bounding boxes do not appear for recorded streams.
</Note>

#### Hardware Profiles and Deployment Paths

Run `nvidia-smi -L` to identify the GPU model, then use the architecture tab below to set `HARDWARE_PROFILE` and the GPU placement for your deployment path.

Set the common deployment variables in `industry-profiles/warehouse-operations/overrides.env`:

| Variable | Description |
| --- | --- |
| `VSS_APPS_DIR` | **Required.** Absolute path to this repository's `deploy/docker` directory. |
| `VSS_DATA_DIR` | **Required.** Absolute path to the extracted warehouse application data directory. |
| `HOST_IP` | **Required.** Host IP address of the machine where the blueprint is deployed. For cloud VMs, use the private instance IP and set `EXTERNAL_IP` to the public IP or hostname. |
| `EXTERNAL_IP` | Required only when clients cannot reach `HOST_IP`; used for externally reachable service URLs. |
| `SAMPLE_VIDEO_DATASET` | Dataset to process. Every included dataset is supported by every Warehouse profile. |
| `NUM_STREAMS` | Number of concurrent streams to process. This must match the camera count of `SAMPLE_VIDEO_DATASET`; it is not selected by system architecture. |

Container image coordinates are centralized in `containers.env` and loaded by the deployment command. In your hardware tab:

1. Copy the settings from **Hardware Profile** into `industry-profiles/warehouse-operations/overrides.env`.
2. Choose exactly one deployment path and copy its settings into the same file.

<Note>
**Switch between Kafka and Redis**

With `ENABLE_PROFILE_CONFIGURATOR=true`, the VSS Configurator uses `STREAM_TYPE` to toggle Kafka or Redis settings for these services:

- Behavior Analytics: updates source and sink type to `kafka` or `redisStream`.
- VST: updates notification message broker consumer settings.
- Video Analytics API: sets `kafka.brokers` to `["localhost:9092"]` for Kafka or `null` for Redis.

#### Elasticsearch ILM policy retention period

<Note>
Elasticsearch data is cleaned up every 4 hours as part of the ILM policy provided as part of the blueprint.
</Note>

To increase the retention period, adjust index lifecycle (ILM) time by setting `ELASTICSEARCH_ILM_MIN_AGE` in `industry-profiles/warehouse-operations/.env` (for example `12h` or `1d`). This value is passed to the Elasticsearch init container when ILM policies are applied.

**Default:** `4h`

```bash

```

For how ILM policies are defined and other tuning options, see [ELK (Elasticsearch, Logstash, Kibana)](/vss/system-components/middleware/database/elk).

### How the Skill Configures and Runs the Deployment

For the Warehouse Blueprint, `vss-deploy-profile` loads
`skills/deployment/vss-deploy-profile/references/warehouse.md` in the VSS Blueprint repository
as its per-profile playbook. That reference owns the warehouse-specific decisions the
Skill makes on the operator's behalf:

* **Profile variants** - picks `bp_wh`, `bp_wh_kafka`, or `bp_wh_redis` with
  `MODE=2d|3d|mv3dt`, or selects `bp_wh_auto_calib` with
  `MODE=auto-calibration`, along with the matching Compose profile list. Dataset
  selection is independent of this choice. See
  [Deployment Selection](/vss/vision-agent/agent-workflows/industry-specific-examples/warehouse-operations-blueprint/quickstart#deployment-selection).
* **Minimal vs extended** - for `bp_wh_kafka` and `bp_wh_redis`, chooses whether to
  deploy ELK, Video Analytics API, and monitoring on top of the core CV pipeline. See
  the Minimal Profile section above for the comparison.
* **GPU layout** - maps services to host GPU device IDs:

  * `RT_CV_DEVICE_ID` - GPU for RT-CV/perception.
  * `RT_VLM_DEVICE_ID` - GPU for `rtvi-vlm` in the `bp_wh` 2D agent profile.
  * `LLM_DEVICE_ID` - GPU for the LLM in `bp_wh` 2D agent profile when using `LLM_MODE=local`. This setting is not used when `LLM_MODE=remote` or `LLM_MODE=none`.
* **LLM placement** - for the `bp_wh` 2D agent profile, picks
  `LLM_MODE=local` or `LLM_MODE=remote` from the user's hardware and request.
  For `bp_wh_kafka` and `bp_wh_redis` in 2D, 3D, or MV3DT mode, and for
  `bp_wh_auto_calib` in auto-calibration mode, sets `LLM_MODE=none`.
* **App data source** - chooses between `<repo>/data`, a custom local path, or the
  `nvstaging/vss-warehouse/vss-warehouse-app-data:v3.3.0-09042026` NGC resource.
* **Calibration** - for own-data deployments, routes to the standalone or warehouse
  auto-calibration profile to generate calibration JSON before the full warehouse stack
  comes up.
* **Bring up and monitor** - runs `docker compose -f compose.yml ... up` with
  `containers.env`, `industry-profiles/warehouse-operations/.env`, and
  `industry-profiles/warehouse-operations/overrides.env`, then watches logs and `docker ps`
  until every expected container reports `Up` and FPS is flowing through
  `vss-rtvi-cv` or `vss-rtvi-cv-mv3dt` for MV3DT.
